## ロックの契機と認証

| 契機 | 動作 | 根拠 |
| --- | --- | --- |

| logind の `PrepareForSleep(true)` | 画面を隠し、入力・コピーを失効、子を停止。完了後にスリープ猶予 FD を解放 | 同ファイル `:25`、`src/main.cpp:498`、`:1080` |

| 5分間のアプリ内無操作 | キー押下、ボタン、タッチ、スクロールで更新する期限に達したらロック。単なるマウス移動や他アプリの操作では延長しない | `src/gnome/SessionGuard.h:8`、`src/main.cpp:275` |

初期の `GetActive` と logind の `PreparingForSleep` も確認する。初期照会の決着までは解除を待ち、同じ所有者の重複通知をサービス差替えと誤認してロックしない。デスクトップがロック中、スリープ準備中、存在する logind の猶予取得が未完了・拒否の場合は DB の新規解除を許可しない。解除と初期復旧コピーの完了後にも状態を再確認してからモデルを画面へ公開する。解除通知自体は DB の鍵を再取得しない。明示的なパスワード入力が必要である。

logind には `Inhibit("sleep", ..., "delay")` を非同期要求する。復帰・サービス再接続後は再取得し、失敗は間隔を置いて再試行する。取得・通知・問い合わせに同期 D-Bus 呼出しを使わず、GUI を無期限に止めない。ロック処理の終了とアプリ自身のクリップボード転送の中止・作業コピー消去を確認してから FD を解放する。終了時もモデル停止を先に行う（`src/main.cpp:40`、`:51`、`:287`、`:1080`）。

監視・猶予を利用できない環境ではバナーを表示する。特に logind 自体が存在しない分離セッション等では、GNOME の通知と無操作期限・復帰時計を併用するが、サスペンド前の完了を保証する経路としては扱わない。logind の最大猶予は OS の設定に従う。割り込み不能なカーネル I/O 等で子を回収できない場合、アプリだけで猶予を延長したり強制サスペンドを防いだりする保証はない。

## 完了した編集をロック前から保護する

**確認済み。** ロック通知を受けてから全 DB の書出しを始める方式は採用していない。重い KDF や I/O がスリープの猶予に収まるとは限らないため、GTK 経路は次の順で処理する。

1. DB 作成・解除後に、上流 writer / reader と既存の読込検査で初期の暗号化復旧コピーを作る。これに成功するまで GTK の解除済みモデルとして公開しない。
2. エントリー／グループの作成・更新・ごみ箱移動等の成功後、同じモデルの暗号化復旧コピーを同期・再読込検証する。
3. 復旧コピーの完了後に限り、その編集操作の成功を返す。元の DB の保存先や dirty 状態は変更しない。
4. コピーの作成に失敗した場合は編集成功を返さず、ワーカーを終了してロックする。それまでに成功した編集のコピーを残し、専用の失敗理由と復旧先を表示する。
5. 自動ロックでは保存の完了を待って鍵を保持せず、中断とモデル停止を要求する。処理途中の未応答操作がコピーに含まれる場合はあるが、完了前の最新操作を常に回収できるとは約束しない。

実装は `src/gnome/session_worker.cpp:76`、`:94`、`:99`、`src/gnome/CheckpointStore.h:16`、`:26`、`prototype/CoreSession.cpp:462`。暗号・鍵導出・KDBX を再実装せず、手順3と同じ上流 writer と検査付き reader を使う。書出しに伴う dirty / non-data-change 状態を復元する。

復旧保存用 RPC と、保護を有効にした編集 RPC は CPU 45秒／経過90秒、1 GiB アドレス空間・128 MiB ファイル長の既存上限で実行する。型・KDF・展開量・XML・モデル上限も継続する。正当な大きい DB でも、通常の解除より初期復旧コピーに大きな資源が必要なため、GTK では保護を開始できずロックする場合がある。上限を黙って緩めたり、失敗した編集を成功として表示したりしない。

私有プロトコルは version 2 とした。復旧保護要求・失敗理由と最新コピーを扱い、異なる版のコントローラー／ワーカーを混ぜた場合は起動時に拒否する（`src/gnome/SessionProtocol.h:18`）。

## 復旧ファイルの保存先・保持・削除

保存先は `$XDG_STATE_HOME/keepassxc-gnome/recovery/`。XDG の既定値を使う通常環境では `~/.local/state/keepassxc-gnome/recovery/` となる。所有者・`0700`・通常ディレクトリであることと、使用開始時の device / inode を検査する。入力 DB の横や平文の一時ファイルへ自動保存する処理は追加していない。

`SafeSave::archive` は、既存の同期・再読込検証を再利用し、`written.kdbx` と `state=checkpoint` の journal を完成させる。通常の DB パスの公開・置換は行わない。候補の一時コピーは完成した復旧コピーから独立しており、データは暗号化した KDBX のまま保管する（`src/gnome/SafeSave.cpp:235`、`:288`）。

- 解除中のセッションごとに直近2個の完成コピーを保持する。新しいコピーが完了してから、そのセッション自身の古い記録だけを既存の安全な削除処理で退役させる。他セッションや利用者の通常保存のバックアップは自動削除しない。
- 使用中の2記録のロック FD を、保存処理から途切れなくワーカーへ引き継ぐ。別プロセスからも使用中の記録を削除できず、一覧ではロック・終了後に表示する（`src/gnome/SafeSave.cpp:244`、`src/gnome/CheckpointStore.h:49`）。
- 私有記録に想定外のファイルがあって古いコピーを削除できない場合は残す。同一セッションで64記録に達すれば次の保護を失敗させる。保持件数は全セッション合計の quota ではないため、利用者による過去の記録の整理が必要である。
- メニューの「未保存の変更を復旧」は、このフォルダーをファイル選択なしで検査する。「コピーを開く」で元の認証情報を入力し、通常の読込検証後、新しい名前で保存する。元の DB への自動反映はしない。
- 手動で未保存変更を破棄・ロック・終了した場合も、既に完成した復旧コピーは残る。既存の破棄確認にも残存することを表示する。削除は使用中でない記録について利用者の確認を伴う。暗号化コピーには過去の秘密も残り、通常のファイル削除を安全消去とは扱わない。

**フォームの境界。** エントリーの「保存」を完了していない入力は、まだ DB モデルの確定した編集ではない。自動ロック時はそのフォームを消去し、暗黙に DB の値へ変換・確定しない。編集画面に「保存すると復旧用コピーで保護される」ことと、この境界を表示する。途中の生成パスワード等も、フォームから保存する前はこの扱いになる。

`explicit_bzero` と破棄時の消去は、アプリが管理する生きた値に対する対策である。Qt の JSON 内部、GTK / GLib、コンパイラーの一時値、アロケーター、OS・スワップ・デバイス、貼付先まで全ての複製を探索し安全消去したという主張ではない。GTK の secure buffer の採用も、全メモリが常に mlock 済みであることを証明するものではない。core dump / dumpable の既存抑止は維持し、ポータルを動かすために解除する変更は行わなかった。

## クリップボード：失効と外部の残留を分ける

以前の [GNOME / Wayland の検証](phase2-desktop-followup.md#フォーカスを失ったクリップボードの対策比較) では、アプリが所有権を放しても Mutter が文字列を再提供するケースを確認済みである。この制約を解決したと表示する変更は行わない。

**実装・確認済み。** アプリのコピー操作では、文字列を無期限の GValue provider に格納する方式を廃止し、失効可能な provider を使う。`CLOCK_BOOTTIME` に基づく10秒の期限を各提供要求で確認し、タイマーが遅れても期限後の新規提供を拒否する。ロック・所有権変更でも失効し、管理するバイト列を上書きする。進行中の転送をキャンセルし、作業コピーは IO 完了後に上書きする。スリープ猶予の解放はこの処理も待つ。永続化用の形式を要求せず、既知のパスワードマネージャー用 MIME ヒントも付ける（`src/gnome/SecretClipboard.cpp:8`、`:26`、`:87`）。

初回のコピーでは、秘密を取得する前に、GNOME や履歴ツールに残る制約を確認する。コピー後も「10秒後に必ず消える」と表示しない。コピー値は1 MiBまでとし、拒否・失効・転送エラーに実際の値を含めない。PRIMARY selection については、ロック時に自分のアプリがローカルに所有するものだけ解放する。

**保証しない範囲。** 期限前に Mutter、履歴管理ソフト、貼付先等が受け取ったコピーは、この provider の失効で取り戻せない。通常のフォーム操作で外へ渡した文字列まで本 provider の期限付きに変換する実装でもない。GNOME 側からの完全な消去を要件とするなら、別の許可・デスクトップ API とそのサービス障害時の設計が必要である。Remote Desktop の広い許可を自動取得したり、GNOME 本体を変更したりする機能は追加していない。

## GUI の終了時割り当ての対照

**観測済み・判定を限定する。** GUI を LeakSanitizer 付きで終了すると、Fontconfig / Pango / GTK の経路を含む割り当て報告が出た。アプリのセッション・モデル・クリップボード・監視コードを一切リンクしない GTK 単体の対照でも、終了時に **661,897 bytes / 16,391 allocations** の報告を再現した（`tests/gtk_memory_control.cpp:1`、`build/ui-gtk-memory-control/app.log`）。これを根拠にアプリ側の全ての報告まで外部由来と断定することはしない。

GUI の sanitizer 実行は `detect_leaks=0` としてメモリアクセス異常の検査に限定する。リークの抑制ファイルで合格扱いにする処理は追加していない。描画を伴わないコア・通信・保存・寿命の試験では `detect_leaks=1` を維持する。GUI 全体の終了時割り当ての評価は、UI と配布環境の仕上げに残す。対照は `bash tools/test-reader-memory.sh --gtk-control` で再現でき、LeakSanitizer の報告が出る環境では非ゼロ終了が想定される。
