# データ互換性の範囲と優先順位

決定日：2026-11-13。利用者の「提案の優先順位で進める」「3は検討した結果を記録として保存するのみ」という指示に基づく。

## 採用する方針

| 優先順位 | 方針 | 扱い |
| --- | --- | --- |
| 1 | 本家 KeePassXC が通常保存する既知データを正しく読み書きし、GTK 未表示のデータも保持する | 実装・検証の最優先。本家との往復で確認する |
| 2 | 保持できない入力を理由付きで拒否する | データ消失防止の必須条件。拒否した入力を互換性対応済みとは数えない |
| 3 | 任意の未知構造を保持して再保存する | 検討記録のみ。現在の実装対象・完成条件・実装予定に含めない |

上流は固定した `1c2f23ef5914c0f442a00533def1689857afb5a7`（2.8.0）を基準とする。将来の上流更新では、基準を更新して通常保存データの試験を継続する。元ファイルを変更せず、コピーを使って合成データと公式リポジトリの試験データだけを検証する。

既知の拡張点の任意キーは、未知構造と区別する。Entry のカスタム属性や CustomData の任意キーは、既存のモデルと writer が扱う既知の構造である。これらや TOTP、添付、履歴、Auto-Type・Browser 等の既存データは、GTK に機能 UI がないことだけを理由に削除しない（`upstream/keepassxc/src/format/KdbxXmlWriter.cpp:416`、`prototype/core_probe.cpp:66`）。

正当な本家データが現在の上限・保護条件・未対応キー方式で拒否される場合は、互換性の制約として記録する。本家の通常データに対する不用意な拒否が見つかったときは、安全性と保持を検証した上で修正を検討する。成功したケースだけを並べ、拒否を黙って除外する運用にはしない。

この方針に基づく最初の[公開テストデータ検証](upstream-fixture-compatibility.md)では、原本3件と現在の本家 CLI で再保存した別コピー2件の往復を確認した。原本2件の拒否は互換性の制約として別に記録した。

さらに、無変更の本家コアで生成する[既知データの40組合せ・80往復](known-data-compatibility.md)を追加した。保存される日時、アイコン、参照等の比較を広げ、コピー時に参照を解決しない不具合を修正した。

## 任意の未知構造についての検討記録

対象を限定した未知メタデータの保持は技術的に検討可能だが、意味・参照関係が分からない任意の構造を編集後も安全に再保存する一般保証はできない。

- 未知の XML 要素・属性・ヘッダーを所属先・順序等とともに保持するモデルと、reader / writer 双方への接続が必要。
- 保護値はストリーム処理の順序に依存する。元の暗号文を保存時にそのまま挿し戻すだけでは保持できない。既存の暗号処理での復号と再暗号化、順序管理が必要（`upstream/keepassxc/src/format/KdbxXmlReader.cpp:1027`、`upstream/keepassxc/src/format/KdbxXmlWriter.cpp:434`）。
- 未知構造が添付番号、UUID、内容のハッシュ等に依存すると、既知データの編集・削除・保存時の振り直しに追従する方法を判断できない場合がある。
- 将来の暗号・KDF・形式を理解できない場合まで保証することはできない。固定した本家自体にも未知 XML を読み飛ばす処理があり、任意未知構造の保持は本家の通常データとの互換性の必須条件ではない（`upstream/keepassxc/src/format/KdbxXmlReader.cpp:1220`）。

これらの複雑性と保守負担を踏まえ、**この機能の実装は行わず、検討結果だけを保存する**。過去の文書にある「未知構造の再保存が未完了」「今後評価する」は当時の状況であり、この決定により開発の未完了項目から外れる。再着手には利用者の新たな指示を要する。

元の暗号化バイト列を変更せずコピーすることは可能だが、編集を反映する再保存とは別であり、この機能の実装や互換性試験の代替として扱わない。

## 残る製品化条件

優先順位3を実装しなくても、既知データの互換性・保持、安全な拒否、資源制限、保存と復旧、画面ロック・スリープ、秘密の寿命、Wayland、言語と明暗、VMでの導入等の条件は引き続き必要。今回の範囲確定によって、アプリ全体が完成・実データ利用可能になったとは扱わない。
