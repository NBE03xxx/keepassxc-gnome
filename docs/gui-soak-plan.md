# 長時間メモリ検証の実施条件

2026-11-13。利用者が手順1を指示。試験開始前に条件を固定する。

- 同一プロセス・同一ウィンドウで約5秒間隔の操作を60分実施し、その後DBをロックしたまま15分待機する。準備・分析を含め約90分を見込む。
- 合成KDBXだけで解除、保護付き編集、コピー、編集フォーム、自動ロック、暗号化復旧コピーの再認証を反復する。実際の画面ロック・スリープ・本番DB・通常のクリップボードは使わず、私有GNOME・D-Busで行う。
- 毎巡、同じロック済み状態と約5秒の経過後にASanの生存割り当て量・確保ヒープ量、RSS、匿名RSS、FD数、スレッド数、Mesaモジュールのマッピング有無を記録する。15分待機中も30秒間隔で記録する。メモリ内容・秘密文字列を記録しない。
- 最初の10分をwarmupとし、以降の10分窓の中央値と回帰傾向を評価する。ASanのquarantineやアロケーター予約領域を含むRSSと、生存割り当て量を区別する。強制GC・malloc_trim・フォントキャッシュ強制終了は行わない。
- 要調査の目安を、warmup後の生存割り当て中央値が最初の窓から最後の窓へ1 MiBまたは5%の大きい方を超えて増加、または傾き64 KiB/分超とする。FD・スレッドの中央値が2を超えて増える場合も調査する。閾値以下をもって全経路のリーク不存在を証明したとは扱わない。
- 最後にフォーム・Window・Applicationのfinalize、ASanアクセス検査、抑制なしLSanと固定版の所有関係の照合を行う。生LSan終了134は保持し、未説明があれば受入しない。
- Vulkan単独の128 bytesは、反復回数・module lifetimeの対照で解析する。外部依存の問題はアプリへの影響と分けて記録し、製品へ強制dlopenなどを加えない。

実装は `tests/lifetime_ui_probe.cpp` と `tests/SoakMetrics.h`、集計は `tools/analyze-gui-soak.py`。製品のテスト用RPC・設定は増やさない。通常の開発パッケージ導入・本家コード変更は不要。
