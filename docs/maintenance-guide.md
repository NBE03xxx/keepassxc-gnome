# 保守・更新・候補固定の実行手順

2026-11-14。[配布設計](distribution-maintenance.md)を日常の保守作業として使うための手順。対象はUbuntu 26.04 / GNOME 50 / Wayland。新しい依存の導入、上流修正、公開操作はAGENTS.mdに従う。

## 定期確認

担当者が通常週1回以上と緊急通知時に、公式KeePassXC release / advisory、Ubuntuの依存更新を確認する。この記載は自動監視を登録したという意味ではない。実行例は `python3 tools/check-upstream.py --output docs/security/upstream-review-日付.json`。

取得失敗はunknownとして扱う。最新タグ・修正版の版比較だけで安全判定せず、到達経路・修正内容・本アプリの独立パッチ・GTK層・依存への影響を記録する。連携機能を無効にしている場合も、将来の有効化を含めて判断する。セキュリティ修正を機能追加より優先する。

## 更新の準備

1. 現在のソース、固定上流、パッチ、依存、未解決事項、検証済み成果物のhashを記録する。既存成果物を上書きしない。
2. 上流の参照checkoutを編集せず、候補を別のcheckoutまたは検証ブランチで確認する。出典・署名を確認する。hash一致と署名検証を混同しない。
3. `packaging/upstream.json`、`cmake/` の接続、パッチの対象とhashを一組で評価する。fuzz適用はしない。本家へ修正が必要な場合は理由を先に報告する。
4. 廃止できる独立パッチは理由と比較結果を残して廃止する。保持拒否・終端・資源制限の検査を迂回して採用しない。
5. 新規依存が必要なら、通常環境かVMか、用途・理由・導入計画を先に提示する。検証環境を用意するために既存KeePassXCを変更しない。

## 検証の入口

通常の入口は `bash tools/check-release.sh`。固定した上流の検証、ビルド、CTest、GUI、ASan、梱包、対応ソースの再ビルド、同一入力の梱包一致を実行する。実インストール・署名・公開・pushは行わない。私有D-Bus / GNOME / AT-SPIを利用できる、合成データだけのUbuntu 26.04 runnerを使う。

Orcaの確認は `bash tools/test-ui.sh --orca` と `KPXC_UI_LANGUAGE=en bash tools/test-ui.sh --orca`。実際のキー入力、フォーカス、保護ロール、伏せ字、読み上げの陽性対照を確認する。発話が無いことだけを成功条件にしない。ログは私有環境の合成文字列に限定する。実機Orcaの詳細な全アプリログは採らない。

読込・保存・互換性に影響する変更では、無変更の上流CLI / reference toolとの往復、raw / IPC両方の保持、失敗・中断・競合・復旧・自動ロックを確認する。GUIや依存の寿命に影響する変更では適切なメモリ検査を加える。公開済みの失敗基準を後から緩めて合格にしない。

## 配布候補

版を上げて `tools/build-deb.py --version 対象版 --output 新しい保存先` から作成する。実行直前に `source tools/dev-env.sh` を使用する。バイナリと同じ完全な対応ソース、manifest、SHA256SUMSを一組で保持する。公開用連絡先等が未確定なら非公開の候補と明示する。

manifestと検証記録には、コミットだけでなく対応ソース全体のhash、パッチ、依存、strip後の3実行ファイル、ツール版を残す。同じ入力の梱包一致と、別のビルド環境でのELFバイト一致は別の主張として扱う。

Ubuntu 26.04 VMでAPT計画を確認し、導入・更新・削除、配置先の実アプリと補助プログラム、locale、GUIを検証する。スナップショットと開始前のパッケージ状態を保持する。失敗時に勝手にsnapshot復元や依存削除を行わない。最後は検証アプリだけを削除し、状態照合と通常shutdownを確認する。詳細は [VM手順](vm-package-test.md)。

実機への更新はVMを通過した同じhashのdebで行う。実機の再確認は動作が変わった箇所に絞り、ユーザーのOS認証や音声確認が必要なら具体的な手順を案内する。同じ実行ファイルを文書・metadataだけ変更して梱包した候補は、既存の実機検証とのhash同一性と差分を明示して評価する。

## 受入・公開・問題発見時

確認済み、推論、未検証、未解決の観測、対象外を分ける。既知の制限をREADME・利用手順・候補の記録へ反映する。コードを変えていない再確認を、不具合の修正とは扱わない。実データ利用と公開の合格判定を明示する。

公開前に [公開用メタデータ](publication-settings.md) の保守者・URL・報告窓口・署名方針等を確定する。対応ソースとバイナリを同時に提供する。署名を採用する場合は、確定した管理者がタグ・checksumsへ署名し、公開鍵の確認方法を案内する。署名なしの場合はその旨を明記し、hashだけで配布者の真正性を保証したとは扱わない。

利用者自身がアプリの起動・操作を一通り確認した後、改めて明示した場合にGitHub公開を行う。確認結果や通常の作業継続だけを公開指示に読み替えない。鍵生成、公開リポジトリ作成、アップロードは明示指示なしに実行しない。

取り込み不能・安全性に未評価の問題があれば、最後に検証した成果物と記録を保持し、理由と利用・配布への影響を報告する。旧版への上書き導入だけでDBの互換性が戻ると考えず、バックアップと形式・設定を確認する。本番DBで再現を求めず、合成の最小例を用意する。外部PRを個人の秘密を持つrunnerで自動実行しない。
