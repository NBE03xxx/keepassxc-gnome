## 接続方法と確認した境界

- **CMake** — 上流をルートプロジェクトのまま構成し、`CMAKE_PROJECT_KeePassXC_INCLUDE` と `cmake_language(DEFER)` で上流ターゲットが定義された後に試作ターゲットを追加した。生成ヘッダー、静的アーカイブ、依存のリンクは既存の `keepassxc_core` を利用する。 `text_stream` も上流のターゲットを利用する。 [接続処理](../prototype/attach.cmake)、[ターゲット定義](../prototype/targets.cmake)、[CMake のプロジェクトフック](https://cmake.org/cmake/help/latest/variable/CMAKE_PROJECT_PROJECT-NAME_INCLUDE.html)
- **KDBX 4.1 の版** — 版情報だけを 4.1 にした合成 DB を読むと、上流の `Database::formatVersion()` がヘッダーと異なるケースを確認した。 `KdbxReader` がヘッダーの版をセットした後、KDF ヘッダーの処理で `Database::setKdf` が必要な版を再計算する。試作は上流の `KeePass2Reader::version()` で読み取ったファイルの版を復号成功後のモデルに引き継ぎ、出力ヘッダーの 4.1 維持を検証した。ヘッダー確認と復号は二回の読み込みなので、外部から変わり得る実ファイルでの保証は別途設計する。 `src/format/KdbxReader.cpp:80-104`、`src/format/Kdbx4Reader.cpp:205-218`、`src/core/Database.cpp:1126-1130`、[試作の解除処理](../prototype/CoreSession.cpp)
- **イベント処理** — GTK は主スレッド、DB 操作は専用 QThread に置いた。GTK の一件実行ガードにより、保存内部のネストした Qt ループへ次の操作を渡さない。保存中にロックが要求された場合は画面と provider を先に破棄し、保存の応答で画面を更新せず、Qt 側で DB を解放する。ファイル監視のチェックサム計算に備え、解放前に上流が使用する Qt スレッドプールの完了を待つ。 `src/core/AsyncTask.h:36-75`、`src/core/Database.cpp:324-355`、`src/core/FileWatcher.cpp:111-146`
- **ポータルとダンプ抑止** — `Bootstrap::disableCoreDumps()` を有効にした試作で、ポータル設定の読み込みとポータル監視の生成が `AccessDenied` になった。ログはポータルが試作プロセスの `/proc/<pid>/root` を開けないと示している。上流にも `PR_SET_DUMPABLE=0` とポータルの干渉に関する記載がある。この試験では明暗を明示設定し、ダンプ抑止を維持した。通常の GNOME 設定に連動した外観とポータル経由のファイル選択は追加検証が必要。 `src/core/Bootstrap.cpp:79-109`

## 再実行

承認済みの Ubuntu deb は 42 個、取得量は 38.8 MB。 `dpkg-deb -x` で作業専用プレフィックスに展開した。CMake とコンパイラーにそのプレフィックスを渡し、展開した Qt CMake 定義から参照される既存ランタイムには同じ版のシステムファイルへのリンクを作業ディレクトリ内に用意した。展開した `.pc` の `prefix=/usr` を作業プレフィックスへ向け、`-lpcsclite` の解決にはビルドプロセスの `LIBRARY_PATH` を指定した。作業パス以外にパッケージの展開は行っていない。

この環境に残っている作業ディレクトリを使用する場合は以下で再実行できる。依存・試験プロファイルは一時ファイルなので、環境を再作成する場合は [依存一覧](phase2-preflight.md#導入の相談対象) と上記の展開手順を使う。

```bash
kpxc_work=/tmp/keepassxc-phase2.YxadbPNq
kpxc_source=/tmp/keepassxc-phase1.tFbFQBIk/source
source "$kpxc_work/build-env.sh"
export LIBRARY_PATH="$kpxc_lib${LIBRARY_PATH:+:$LIBRARY_PATH}"

cmake -S "$kpxc_source" -B "$kpxc_work/upstream-build" -G Ninja \
  -DCMAKE_BUILD_TYPE=Release -DKPXC_MINIMAL=ON -DKPXC_FEATURE_NETWORK=OFF \
  -DKPXC_FEATURE_DOCS=OFF -DWITH_X11=OFF -DWITH_TESTS=ON -DWITH_GUI_TESTS=OFF \
  -DKPXC_PHASE2_GTK=ON -DCMAKE_PROJECT_KeePassXC_INCLUDE="$PWD/prototype/attach.cmake"
cmake --build "$kpxc_work/upstream-build" --target phase2_core_probe phase2_gtk_probe
ctest --test-dir "$kpxc_work/upstream-build" --output-on-failure -R '^phase2_core_probe$'
```

手動確認では `GDK_BACKEND=wayland "$kpxc_work/upstream-build/phase2_gtk_probe"` でウィンドウを起動する。起動時に専用の一時ディレクトリに合成 DB が作られ、表示された試験用パスワードで解除できる。編集内容は別ファイルへ保存し、ファイル選択の受け入れ対象は試作が生成したパスだけ。自動試験でクリップボードを扱う際は `dbus-run-session`、専用の `XDG_RUNTIME_DIR` と Wayland ソケットを用い、`gnome-shell --wayland --headless --no-x11 --virtual-monitor=960x640` で別コンポジターを開始する。期限切れは `--smoke-test`、所有権の置換は `--smoke-test-replacement` で、各試験に別セッションを使用する。

## 外部更新と保存失敗時のデータ保全

確認日 2026-11-08。上流 2.8.0 固定版と `develop` 更新候補のビルド済みコア、Qt 6.10.2 を使用した。合成 KDBX 4.0 で tmpfs と ext4 の両方を試し、固定版の ext4 では KDBX 3.1 と 4.1 を入力にした試験も行った。シンボリックリンクと `QLockFile` の追加試験は両ビルドの KDBX 4.0 と ext4 で実施した。保存前後の SHA-256、編集状態、上流リーダーで読み直したエントリーを比較した。すべて合成データで検証し、通常環境への開発パッケージ追加は不要だった。

### 確認済み

| 条件 | 結果 |
| --- | --- |
| 開いた後、保存を始める前に別の有効な KDBX へ置換 | 上流のコアは未マージの変更として保存を拒否した。外部ファイルと試作側の未保存編集は残った |
| 外部から先頭 1 KiB より後ろの暗号化データを 1 バイト変更 | 上流コアの保存は変更を検出せず、メモリー上の編集内容で置き換えた |
| 外部から元ファイルを削除、または 64 バイトに切り詰め | 削除されたファイルを再作成し、切り詰められたファイルを置き換えた |
| 保存先ディレクトリの書き込み権限を除く | 保存は失敗し、元ファイルの SHA-256 と未保存編集を保持した |
| プロセスの `RLIMIT_FSIZE` で一時ファイルへの書き込みを途中で失敗させる | 保存は失敗し、元ファイルの SHA-256 と未保存編集を保持した |
| 保存先への公開に使うシステムコールを `EACCES` にする | 一時ファイルへ書いた後の公開に失敗し、元ファイルの SHA-256 と未保存編集を保持した。以上の三つの失敗条件を解除すると、同じ DB の再保存に成功した |
| バックアップ先にファイルを作れない | 上流コアの Atomic 保存は成功を返し、元ファイルは新しい内容に置き換わった |
| 外部の有効な KDBX を、照合が終わった後の公開直前に配置 | 上流コアの上書き保存は成功を返し、その外部ファイルを置き換えた |
| 別名保存先に、存在確認の後で別の有効な KDBX を作成 | 変更前の `CoreSession::saveCopy` はそのファイルを置き換えた。読み込み元の SHA-256 は維持された |
| 別名保存先に、参照先が存在しないシンボリックリンクを置く | 変更前の `saveCopy` はリンクの先へ DB を書き込んだ。リンクと読み込み元は残った |
| 上流コアで暗号化した候補を同一ファイルシステムから `renameat2(RENAME_NOREPLACE)` で公開 | 保存先にファイルやシンボリックリンクがあれば `EEXIST` を返し、既存の項目も候補も保持した。空いている名前への公開後は、上流リーダーで編集済み DB を読み直せた |
| 試験側が同じパスの `QLockFile` を保持している間に別ライターを起動 | 同じロックに従う呼び出しは拒否された。変更を加えていない上流 CLI の `add` は合成 DB を更新できた |

公開直前の置換と公開時の失敗は、試験プロセスだけで有効な `LD_PRELOAD` の小さなシムで再現した。合成ファイルに限定し、`rename` または `linkat` が対象パスを公開する直前に別ライターの置換を差し込むか、その呼び出しを失敗させた。競合の順序を固定しており、同期ソフトを使った試験とは区別する。既存の `phase2_core_probe` は両ビルドで再実行して通過した。

上流コアは現在のパスを保存するとき、読み込み時に保持した先頭 1 KiB の MD5 と保存前の値を照合する。ファイルが消えた場合や先頭 1 KiB を読めないほど短い場合、変更として扱う分岐を通らない。外部変更が検出されたときのマージ、上書き、編集の破棄は上流 Qt GUI の選択肢であり、コアの呼び出しだけで同じ操作は提供されない。また、上流コアのバックアップ処理は成否を返すが、`performSave` はその値を使って保存を中止しない。 [照合範囲](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/core/Database.h#L77-L84)、[読み込み時の記録](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/core/Database.cpp#L162-L192)、[保存前の照合](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/core/Database.cpp#L269-L355)、[マージなどの選択](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/gui/DatabaseWidget.cpp#L2256-L2296)、[Atomic 保存とバックアップ呼び出し](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/core/Database.cpp#L358-L395)、[バックアップの実装](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/core/Database.cpp#L588-L610)

### 技術的な判断と残る条件

新規の別名保存では、上流コアで同一ファイルシステム内の作業領域に暗号化した候補を作り、保存先が空いている場合だけ一回のシステムコールで公開する方式が候補になった。公開の原子性と上書き防止を確認し、次節で試作に組み込んだ。 [Linux の `RENAME_NOREPLACE`](https://man7.org/linux/man-pages/man2/rename.2.html)

既存ファイルへの上書きは、開いたときの全体ハッシュを保存直前にも照合すれば早い変更を検出できる。ただし、照合と公開の間に別のライターが変更できる。同じロックに参加しないライターには `QLockFile` が効かないため、製品側で制御できないライターを含む経路での上書き保存は保留する。上書きを設計する段階では、元の版の復旧を独立して検証し、必要なバックアップを確定できない場合に元ファイルを保持する条件が要る。Qt の `QSaveFile::commit()` は同期処理のエラーを無視するため、今回の正常終了と障害注入から電源断後の永続性までは確認できない。NFS、FUSE、同期フォルダーでの競合と、保存に失敗した状態でのロックは未検証。 [Qt のロックの適用範囲](https://doc.qt.io/qt-6/qlockfile.html#details)、[Qt 6.10.2 のリンク先解決](https://github.com/qt/qtbase/blob/v6.10.2/src/corelib/io/qsavefile.cpp#L157-L178)、[Qt 6.10.2 の `commit()` 実装](https://github.com/qt/qtbase/blob/v6.10.2/src/corelib/io/qsavefile.cpp#L262-L309)

作業用環境が残っている場合は、プロジェクトのルートから `bash /tmp/keepassxc-phase2.YxadbPNq/save-safety/run.sh upstream-build ext4 4.0` で再実行できる。第一引数に `develop-build`、第二引数に `tmpfs` も指定できる。シンボリックリンクとロックの追加試験には、`KPXC_PROBE_CLI` に対象ビルドの `src/cli/keepassxc-cli` の絶対パスを渡す。試験コードと結果ログは同じ作業ディレクトリにある。

## 試作の別名保存に上書き防止を組み込む

合成 fixture の初回生成と GTK の別名保存は、保存先の親ディレクトリ内に一時ディレクトリを作り、上流の `Database::saveAs(Atomic)` で候補を暗号化する。候補の権限を所有者のみの読み書きに設定してから、`renameat2(RENAME_NOREPLACE)` で公開する。保存先が既存ファイル、リンク、または競合で後から作られたファイルなら、上書きせずに失敗を返す。失敗時も同じ編集セッションで別名を試せる。通常の成功・失敗時は一時ディレクトリを破棄する。 [別名保存の実装](../prototype/CoreSession.cpp#L34-L69)

解除した DB は、読み込み元から切り離した編集用スナップショットとして扱う。上流の `saveAs` は保存パスと監視先を更新し、編集済みフラグをクリアする。試作は候補を書いた後に一時パスとの関連付けを解除し、保存前の編集フラグを復元する。コピーは公開に成功した時点で GTK の選択候補に記録し、ロックが割り込んだ場合も成功済みのパスは記録する。試作では元ファイルを継続監視してマージする動作は扱わない。 [解除時の切り離し](../prototype/CoreSession.cpp#L125-L148)、[GTK の完了処理](../prototype/gtk_probe.cpp#L355-L376)、[GTK の保存処理](../prototype/gtk_probe.cpp#L572-L586)、[上流の保存成功時の更新](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/core/Database.cpp#L335-L353)、[上流の別名バックアップにおける状態復元](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/gui/DatabaseWidget.cpp#L2670-L2686)

固定版と `develop` の両方で、ext4 と tmpfs 上の `renameat2` 呼び出し直前に別の合成 DB を配置した。競合側と読み込み元の SHA-256 は一致したままで、未保存のタイトル編集も残った。公開を `EACCES` で拒否する試験では完成ファイルや一時ファイルが残らず、続けて別名保存して、権限が `0600` のコピーを再解除できた。既存のコア試験も両ビルドで通過し、KDBX 3.1、4.0、4.1 の往復に加えて、参照先のないシンボリックリンクを拒否するケースを追加した。模擬サスペンドが保存中に割り込む既存の GTK 試験も両ビルドで通過した。 [コア試験](../prototype/core_probe.cpp#L122-L166)

### 設計上の判断と未検証事項

## 強制終了後の暗号化コピーの復旧

合成 KDBX 4.0 を使い、アプリ専用の復旧ディレクトリを介する方式を独立した試験プロセスで検証した。前節の試験用ライターで暗号化候補を作り、復旧時は候補を解除してから暗号化済みのバイト列を別ファイルへコピーした。作業ディレクトリの所有者と権限 `0700`、候補の所有者と権限 `0600` を確認し、候補をディレクトリ記述子から開く。上流 CLI の `ls` は復旧候補を開けるか調べる試験に使い、一覧の出力は破棄した。 [上流 CLI の解除処理](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/cli/DatabaseCommand.cpp#L45-L63)、[上流の `Database::open` 呼び出し](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/cli/Utils.cpp#L208-L214)

保存側は候補を作り始める前に、専用ディレクトリの固定ロックファイルに共有 `flock` を取る。列挙と復旧は同じファイルに非ブロッキングの排他ロックを取り、競合時は処理中と判断する。ロックファイルは削除せず、プロセスが生きているかの判定を PID ファイルや経過時間に頼らない。暗号化を担当する試験子プロセスにも同じロックの記述子を渡した。Linux の `flock` は、同じオープンファイル記述を参照する全記述子が閉じると解放される。 [Linux の `flock(2)`](https://man7.org/linux/man-pages/man2/flock.2.html)

準備完了の `ready.kdbx` と、その名前に切り替える前に中断した `writing.kdbx` を分ける。どちらもユーザーが明示的に選んだ候補だけを解除して検証する。復旧先では、暗号化コピーを書いた記述子を `fsync()` してから `renameat2(RENAME_NOREPLACE)` で公開し、保存先ディレクトリを `fsync()` する。試験では同期が完了した場合も候補を保持した。 [Linux の `renameat2(2)`](https://man7.org/linux/man-pages/man2/rename.2.html)、[Linux の `fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html)

### 確認済み

上流 2.8.0 と `develop` のそれぞれで、復旧用ディレクトリと復旧先を ext4 と tmpfs の全組み合わせに置いた。異なるファイルシステムをまたぐ組み合わせを含め、8 組み合わせで各 11 ケース、計 88 ケースが通過した。

| 試験 | 確認した結果 |
| --- | --- |
| 保存側を `SIGSTOP` で停止し、列挙・復旧を試行 | ロック競合を返した。`SIGCONT` で保存を再開でき、`SIGKILL` で終了した場合はロックが解放され、残った候補を列挙できた |
| `ready.kdbx` への切り替え直前に `SIGKILL` | 暗号化済みの `writing.kdbx` が残った。「中断した保存」の経路で明示的に選び、上流 CLI で解除に成功してから復旧できた。ライターの未確定な一時ファイルは保持し、列挙から外した |
| 誤パスワード、破損、想定外のファイル種別や権限 | 誤パスワードと破損は上流の解除処理で拒否され、出力が作られなかった。パストラバーサル、シンボリックリンク、FIFO、ハードリンク、権限が広い候補ディレクトリを拒否した |

| 復旧先のファイル同期またはディレクトリ同期に `EIO` | ファイル同期エラーでは公開を止めた。ディレクトリ同期エラーでは「公開済みで同期未確認」を返し、公開済みコピーと復旧元の両方を保持した |
| 復旧側を公開直前に `SIGKILL` | 同時に試した別の復旧はロック競合で止まった。終了後に復旧元と所有者専用の暗号化一時ファイルが残り、復旧元から再試行できた |
| 復旧成功 | 復旧先と復旧元候補の SHA-256 が一致した。元の入力 DB の SHA-256 も変化せず、上流 CLI で編集後のタイトルを確認できた |

### 設計上の判断と残る条件

専用ディレクトリ内のロックと明示的な解除を組み合わせれば、協調するプロセスの保存と復旧を分離できる。専用ディレクトリ全体をロックするため、別候補の保存中も列挙を待つ。復旧の採用に向けては、候補をいつまで保持するか、復旧成功を確認した利用者がどう削除するか、復旧処理が中断して保存先に残った一時ファイルをどう扱うかを決める必要がある。専用ディレクトリとその親を信頼できるローカル領域に置くことを前提とした。通常の保存・GTK への統合と、OS や電源が停止した場合の永続性は未検証。プロジェクトの試作や上流のソースへの反映は保留し、通常環境へのパッケージ追加は行わなかった。

試験コードは `/tmp/keepassxc-phase2.YxadbPNq/recovery` に置いた。`inbox.py:60-118` がロックと候補の準備・列挙、`inbox.py:121-163` が解除確認と復旧、`cases.py` が障害試験。作業環境が残っている場合は、プロジェクトのルートから `bash /tmp/keepassxc-phase2.YxadbPNq/recovery/run.sh upstream-build ext4 tmpfs` で実行できる。第二引数が復旧用ディレクトリ、第三引数が復旧先のファイルシステムで、第一引数は `develop-build` に切り替えられる。

## 仮想マシンの強制停止後に別名保存を確認する試験

QEMU 10.2.1 の TCG と Ubuntu カーネル `7.0.0-42-generic` で、合成 KDBX 4.0 を置いた ext4 の試験用ディスクを起動した。ext4 はバックグラウンドのジャーナルコミット間隔を `commit=600` とし、指定した処理段階と定期コミットが重なる機会を減らした。カーネルは Ubuntu 公式アーカイブの `linux-image-7.0.0-42-generic` `7.0.0-42.42` を APT インデックスの SHA-256 と照合し、作業用ディレクトリに展開した。ゲストはネットワークとホスト共有を無効にし、ホストの通常環境へのパッケージ追加は行わなかった。 [QEMU の起動オプション](https://www.qemu.org/docs/master/system/invocation.html)

ゲストで現行試作と同期確認付きの試験用アダプターをそれぞれ動かした。シリアルに保存段階を出力した直後に QEMU プロセスを `SIGKILL` し、ゲストを通常終了させずに止めた。同じディスクの状態から新しいゲストを起動し、ext4 をマウントして、元 DB の SHA-256、保存先と暗号化候補の有無を確認した。残ったファイルは上流 CLI で解除し、編集後のタイトルと権限 `0600` を確認した。 [現行試作の別名保存](../prototype/CoreSession.cpp#L34-L68)

| ディスクのモデル | 試験条件 |
| --- | --- |
| QEMU の raw イメージ | ホストの tmpfs 上に置いたイメージを `cache=writeback` で接続し、ゲスト停止後もホストが動作する条件で確認 |
| 揮発性ストレージを模した NBD | 通常の書き込みは揮発領域に置き、`FLUSH` または `FUA` で確定した領域を次のゲストに引き継いだ。テスト用の書き込みで、同期前に見えていたデータが切断後に破棄され、同期を受けたデータが残ることを別途確認した。 [NBD の書き込み順序と同期の仕様](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md#ordering-of-messages-and-writes) |

### 確認済み

KeePassXC 2.8.0 と `develop` のそれぞれで、二つのディスクモデルを使って 7 通りの停止点を試した。計 28 ケースで元 DB の SHA-256 は変化しなかった。次の結果は両ビルド・両モデルで共通だった。

| 強制停止の時点 | 再起動後の結果 |
| --- | --- |
| ファイルの `fsync()` 直前、または成功直後 | 保存先も一時候補も残らなかった |
| `renameat2(RENAME_NOREPLACE)` の直前 | 保存先も一時候補も残らなかった |
| `renameat2` の成功直後でディレクトリ同期の前 | 保存先も一時候補も残らなかった |
| 保存先ディレクトリの `fsync()` 成功直後 | 保存先に `0600` のコピーが残り、上流 CLI で解除して編集後のタイトルを確認できた |
| 同期確認付きアダプターが成功を返した直後 | コピーが残り、上流 CLI で解除できた |
| 現行試作の別名保存が成功を返した直後 | 保存先も一時候補も残らなかった |

NBD の記録では、ファイル同期の完了から名前の切り替え直後まで、書き込み回数と `FLUSH` 回数は増えなかった。ディレクトリ同期の完了時には追加の書き込みと `FLUSH` があった。この条件では、ゲスト内で保存先の名前が見えた後も、その更新がストレージに届く前にゲストを停止できた。現行試作は `renameat2()` の結果だけで保存成功を判定する。 [現行試作の戻り値](../prototype/CoreSession.cpp#L61-L68)、[ファイル同期とディレクトリ同期の違い](https://man7.org/linux/man-pages/man2/fsync.2.html)

プロセスだけを強制終了した場合には残った一時候補が、ゲスト全体を停止した試験では失われた。ゲスト停止後にも候補を残す設計では、準備完了を示す名前と復旧ディレクトリへの登録についても、必要なディレクトリ同期を確認する。今回の対象は別名保存と仮想ディスク上の ext4。復旧用ディレクトリを含む一連の動作は次節で扱う。実機の電源断、物理ストレージのキャッシュと部分書き込み、他のファイルシステムは未検証。プロジェクトで管理する試作と上流のソースへの反映は保留した。

## 仮想マシンの強制停止をまたぐ別ディスクへの復旧

前節と同じ QEMU、カーネル、二つのストレージモデルを使い、ゲスト内で復旧試験用の `inbox.py` を動かした。元の合成 KDBX 4.0 と復旧用ディレクトリを一方の ext4 ディスク、復旧先を別の ext4 ディスクに置いた。両方を `commit=600` でマウントし、デバイス ID が異なることを確認した。復旧用ディレクトリ自体と固定ロックファイルは、試験対象の候補を作る前に同期した。ゲスト用の Python は既存環境の実行ファイルと標準ライブラリを一時イメージに同梱した。

候補を登録する途中でゲストを強制停止し、再起動後に「準備完了」と「中断した保存」の両方を列挙した。復旧途中の試験は、候補を作ったゲストを `ready.kdbx` とその親ディレクトリの同期後に強制停止したディスクを、各ケースの開始点に使った。再起動後は残った候補と復旧先を上流 CLI で解除し、編集済みタイトル、権限 `0600`、候補とコピーの SHA-256 の一致を照合した。候補が残っていれば、新しいファイル名への復旧も毎回試した。 [上流 CLI の解除処理](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/cli/DatabaseCommand.cpp#L45-L63)

### 確認済み

KeePassXC 2.8.0 と `develop` のそれぞれで、raw イメージと揮発性ストレージを模した NBD を使い、候補登録中の 5 点と復旧中の 4 点で停止した。計 36 ケースで元 DB の SHA-256 は変化せず、以下の結果は両ビルド・両ストレージモデルで一致した。

| 強制停止の時点 | 再起動後の結果 |
| --- | --- |
| 候補ファイルの `fsync()` 直前 | 復旧可能な候補は残らなかった |
| `writing.kdbx` の同期済み保存後、`ready.kdbx` への切り替えの直前または直後 | `writing.kdbx` が残った。切り替え直後の停止でも、再起動後には切り替え前の名前で見つかった。「中断した保存」から解除し、別ディスクに復旧できた |
| `ready.kdbx` が入るジョブディレクトリの同期直後、または上位の復旧用ディレクトリも同期した直後 | `ready.kdbx` が残り、再起動後に別ディスクへ復旧できた |
| 復旧先で最終ファイル名への切り替え直前、または切り替え直後で復旧先ディレクトリの同期前 | 最終ファイル名は残らず、復旧先に暗号化済みの一時ファイルが残った。復旧元の `ready.kdbx` を使って別名で再試行できた |
| 復旧先ディレクトリの `fsync()` 成功直後、または復旧が成功を返した直後 | 復旧先の最終ファイルと復旧元の `ready.kdbx` が両方残った。両方を解除でき、SHA-256 は一致した |

### 設計上の判断と残る条件

この ext4 構成では、ジョブディレクトリの同期までで `ready.kdbx` が見つかった。試験用の復旧処理はジョブディレクトリとその上位の復旧用ディレクトリを順に同期してから準備完了を返す。復旧先の同期が終わるまで候補を保持しておけば、別ディスクへの公開が中断しても、検証済みの候補から再試行できる。暗号化一時ファイルや復旧済みの候補をいつ削除するか、GTK で候補をどう提示するか、実機の電源断時の挙動は未検証。プロジェクトで管理する試作への反映は保留し、通常環境へのパッケージ追加は行わなかった。 [Linux のディレクトリ同期](https://man7.org/linux/man-pages/man2/fsync.2.html)

試験コードとログは `/tmp/keepassxc-phase2.YxadbPNq/vm-recovery` に置いた。`inbox.py:105-163` が候補登録と復旧、`guest-recovery.py:59-130` が再起動後の照合と停止点、`run.py:48-123` がゲストの制御。作業用環境が残っている場合は `python3 /tmp/keepassxc-phase2.YxadbPNq/vm-recovery/run.py upstream-build raw` で再実行できる。ビルドは `develop-build`、ストレージモデルは `volatile` も指定できる。

## 復旧済み候補の明示的な削除

復旧したコピーを再確認してから、利用者の明示操作に相当する呼び出しで候補を削除する経路を、合成 KDBX 4.0 で試した。復旧時のファイルと保存先ディレクトリの両方の同期が成功したときだけ、復旧の記録をプロセス内に保持する。この記録は、復旧先の書き込みに使った記述子から取得したファイル識別情報、候補の識別情報、暗号化済みデータの SHA-256 を持つ。ディレクトリ同期に失敗した場合は、復旧先にコピーが見えていても削除できる記録を発行しない。記録をディスクに保存する仕組みは設けず、再起動時は残った候補を保持する。 [Linux のファイルとディレクトリの同期](https://man7.org/linux/man-pages/man2/fsync.2.html)

削除時は復旧ディレクトリを排他ロックする。所有者だけがアクセスできる復旧先ディレクトリに範囲を絞り、復旧元と復旧先のファイル識別情報と SHA-256 を比較し、上流 CLI で復旧先を解除する。直前に両方の名前が照合済みファイルを指すことを確認し、候補だけを `unlinkat()` 相当の処理で削除する。候補が入っていたディレクトリを同期し、完了と同期未確認を区別する。固定ロックファイルとジョブディレクトリは保持した。 [Linux の `unlinkat(2)`](https://man7.org/linux/man-pages/man2/unlink.2.html)

### ローカルで確認した結果

KeePassXC 2.8.0 と `develop` をそれぞれ ext4 と tmpfs で実行し、各 12 ケース、計 48 ケースが通過した。復旧先の消失・内容変更・同じバイト列を持つ別ファイルへの置換、復旧元候補の置換、誤パスワードでは候補を保持した。復旧先のファイル同期またはディレクトリ同期に `EIO` が出た場合も保持した。候補を削除した後のディレクトリ同期に `EIO` を返すと、実行中の OS では候補が見えなくなり、試作は「削除済みで同期未確認」を返した。同期が成功した場合は、準備完了の候補と「中断した保存」の候補のどちらも明示的に削除できた。元 DB の SHA-256 は変化しなかった。

別の境界試験では、協調しない同一ユーザーのプロセスを模し、最後の照合と候補の削除の間に復旧先を別名へ移動した。候補は削除され、照合した名前からは復旧先が消えた。コピー自体は移動先に残った。権限 `0700` のディレクトリでも、同一ユーザーによる変更と候補削除を二つのディスクにまたがって一体化することはできない。試作の削除判断は、復旧先の名前と内容への変更を管理できる領域に限って評価する。

前節と同じ QEMU と二つの ext4 ディスクを使い、別ディスクへの復旧と再解除を済ませたうえで、削除操作の前後にゲストを強制停止した。KeePassXC 2.8.0 と `develop`、raw イメージと揮発性ストレージを模した NBD で各 4 点、計 16 ケース。すべてで元 DB の SHA-256 は変化せず、復旧先を再起動後に解除し、停止前と同じ SHA-256 および編集済みタイトルを確認した。

## GTK で復旧候補を選択して別名保存する試験

GTK4 / libadwaita 試作の一時コピーに、合成 DB 専用の `--recovery-fixture` モードを加えた。ロック中に復旧用ディレクトリの一覧を更新し、「準備完了」と「中断した保存」を識別子付きで表示する。利用者が候補を選び、合成 DB のパスワードを入力して、別名保存を指示する。復旧先は試作が管理する一時ディレクトリに限定し、候補は保持した。 [既存の GTK と Qt ワーカーの接続](../prototype/gtk_probe.cpp#L96-L131)

## GTK の復旧処理と画面ロック・サスペンド通知

合成 KDBX 4.0 を使い、隔離した GNOME Wayland の試験用 D-Bus 上で画面ロックの `ActiveChanged` と logind の `PrepareForSleep` を送った。GTK のボタンと入力欄は AT-SPI で操作した。保存の各段階でワーカーを停止・再開できるシムを試作プロセスにだけ読み込ませ、模擬 logind が渡した待機用ファイル記述子の開閉を別プロセスで観察した。 [systemd のサスペンド通知と待機](https://systemd.io/INHIBITOR_LOCKS/)

変更前の 2.8.0 試作は、復旧中も画面上は DB がロック済みであるため、公開後のディレクトリ同期でワーカーが止まっている間に待機用記述子を閉じた。ワーカー再開後に同期エラーを返しても、ロック処理が復旧結果の表示を無効化していたため、同期警告は表示されなかった。

作業用コピーでは復旧中もロック完了待ちの対象に含めた。通知を受けたら候補一覧を消し、パスワード欄を空にしてワーカーにキャンセルを通知する。ワーカーは解除前後、コピー中、最終名への切り替え直前に通知を確認する。すでに公開されたコピーは選択可能なファイルとして登録し、同期結果をロック完了時にも表示する。サスペンド待機の記述子はワーカーとロック処理の完了後に閉じる。

## 通常の別名保存から復旧候補を登録する試験

GTK 試作の作業用コピーで、復旧モードの通常の別名保存ボタンを、復旧候補の登録と保存先への公開につないだ。試験用の復旧ディレクトリと固定ロックファイルを起動前に用意した。保存は既存の Qt ワーカーで実行し、復旧ディレクトリの共有 `flock` を保持したまま、ジョブ専用のディレクトリを作る。上流ライターで候補を一度暗号化して `writing.kdbx` として同期し、`ready.kdbx` へ切り替えた後、ジョブディレクトリと復旧ディレクトリを順に同期した。 [上流の KDBX ライター](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/format/KeePass2Writer.cpp#L117-L141)、[Linux の `flock(2)`](https://man7.org/linux/man-pages/man2/flock.2.html)

候補の同期が確認できた場合に限り、暗号化済みのバイト列をアプリが管理する別名保存先へコピーした。ファイルを同期し、上書きを禁止した名前の切り替えで公開してから、保存先ディレクトリを同期した。GTK では候補の作成失敗、候補の同期未確認、候補を保持した公開失敗、公開済みで同期未確認、保存成功を分けて表示した。候補は保存成功時にも保持した。 [Linux の `renameat2(2)`](https://man7.org/linux/man-pages/man2/rename.2.html)、[Linux の `fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html)

## C++ の候補登録付き保存とゲスト強制停止

前節で GTK が呼んだ `CoreSession.cpp` とヘッダーを同じ内容でゲスト用の試験プログラムにリンクした。保存時は `saveCopyWithRecovery()`、再起動後の復旧時は `listRecovery()`、`prepareRecoveryTarget()`、`restoreRecovery()` を使う。QEMU、カーネル、raw と揮発性ストレージを模した NBD は前の強制停止試験と同じ構成を使った。元の合成 KDBX 4.0 と復旧候補を一方のディスク、通常の保存先と復旧先をもう一方のディスクに置き、両方を ext4 の `commit=600` でマウントした。 [GTK から呼ぶ C++ ワーカーの構成](../prototype/gtk_probe.cpp#L96-L131)

指定した処理段階をシリアルへ出力した直後に QEMU を `SIGKILL` し、ディスクから新しいゲストを起動した。元 DB、残った候補、通常の保存先、再起動後の復旧先を SHA-256 で比較し、編集後のタイトルとファイル権限 `0600` を上流 CLI と `stat` で確認した。競合試験では、最終ファイル名への切り替え直前に別の合成ファイルを作って同期し、C++ 試作が公開を拒否してから停止した。

### 確認済み

| 強制停止の時点 | 再起動後の結果 |
| --- | --- |
| 候補ファイルの `fsync()` 直前 | 一覧に出る候補と通常の保存先は残らなかった。NBD 側では同期未確定のセクターが記録され、再起動用のイメージから除外された |
| `writing.kdbx` の同期後、`ready.kdbx` への切り替え直前または直後 | `writing.kdbx` が残った。「中断した保存」として再起動後に復旧できた |
| 候補のジョブディレクトリと復旧用ディレクトリの同期後 | `ready.kdbx` が残った。通常の保存先は作られておらず、候補から別名へ復旧できた |
| 通常の保存先で `renameat2()` が成功した直後で、保存先ディレクトリの同期前 | 通常の保存先の最終名は残らなかった。`ready.kdbx` から復旧できた |

| 別プロセス相当の競合ファイルを同期し、試作が公開失敗を返した直後 | 競合ファイルを保持し、`ready.kdbx` から復旧できた。保存先ディレクトリにも、候補と同じ暗号化済みの一時ファイルが見つかった |

競合条件を両ビルド・両モデルで計 4 回再試験し、停止直前と再起動後を比較した。停止直前のゲストでは一時ファイルが消えていたが、再起動後には再び見つかった。

### 設計上の判断と残る条件

この構成では、復旧用ディレクトリの同期後から通常の保存先の同期が終わるまで、先に確定した候補を使って復旧できた。競合時に保存先に残った一時ファイルは候補とバイト単位で一致し、権限は `0600` だった。競合側のディレクトリ同期が一時ファイルの名前も確定させた一方、公開失敗後の後片付けは保存先ディレクトリを同期しないため、再起動時にその名前が戻り得ると考えられる。残存した一時ファイルの識別と回収、既存 DB を上書きする経路、実機の電源断や異なるファイルシステムは今後の検証対象。通常環境へのパッケージ追加は行わなかった。 [Qt の一時ファイル削除](https://doc.qt.io/qt-6/qtemporaryfile.html#dtor.QTemporaryFile)、[Linux のディレクトリ同期](https://man7.org/linux/man-pages/man2/fsync.2.html)

## 無名の一時ファイルから最終名へ公開する試験

競合後の再起動で一時名が戻る現象を比較するため、GTK 試作の作業用コピーで、公開用の一時ファイルを `openat(O_TMPFILE)` に切り替えた。確保済みの保存先ディレクトリ記述子を使って無名のファイルを作り、権限を `0600` に設定した。`QFile` を介して上流ライターまたは暗号化済みバイト列のコピー処理を使い、書き込んだ記述子を同期した。最後に、`/proc/self/fd` でその記述子を指定し、`linkat(AT_SYMLINK_FOLLOW)` で最終名だけを付けてディレクトリを同期する。既存の最終名に対する `linkat()` は `EEXIST` を返す。 [Linux の `O_TMPFILE`](https://man7.org/linux/man-pages/man2/open.2.html)、[Linux の `linkat(2)`](https://man7.org/linux/man-pages/man2/link.2.html)

上流コアと候補の登録手順は従来の経路を使った。復旧用ディレクトリで `writing.kdbx` が準備できた後は、従来どおり `ready.kdbx` に切り替えて同期する。公開用の処理で無名のファイルを開けない場合は、その保存を止めて、すでに登録されている候補を保持する設計とした。 [上流の KDBX ライター](https://github.com/keepassxreboot/keepassxc/blob/1c2f23ef5914c0f442a00533def1689857afb5a7/src/format/KeePass2Writer.cpp#L117-L141)

## 復旧候補の保管上限と保存の競合

正常な保存でも復旧候補を保持するため、作業用コピーで候補の件数と暗号化ファイルの論理バイト数に上限を設けた。保管場所の `.lock` を排他で取得し、確認から新しい候補の登録と別名コピーの公開まで保持する。準備完了の `ready.kdbx` と中断した `writing.kdbx` はどちらも件数とバイト数に含め、以前からある空のジョブは件数に含める。想定外の名前やハードリンクなどを検出した場合は保存を止める。既存候補は自動で削除しない。

新しい候補のサイズは、無名ファイルに暗号化済みの内容を書き出した時点で比較する。残りのバイト数を超えた場合は名前を付けずに閉じ、その処理が作った空のジョブだけを片付ける。登録前のファイル同期エラーでも同じ片付けを行う。ジョブ作成後に強制終了した場合は空のジョブが残り得るため、次回の保存で件数に含める。根拠は作業用の `prototype/CoreSession.cpp:218` のロック取得、同ファイルの `:250` と `:276` の保管場所の走査と候補検査、同ファイルの `:585` の保存経路。

### 確認済み

2.8.0 と `develop` のそれぞれで、ext4 と tmpfs の合計 4 組み合わせを使い、C++ の合成 KDBX 4.0 で各 9 項目を確認した。

| 条件 | 結果 |
| --- | --- |
| 既存候補で件数上限に到達 | 新しい保存先を作らず、既存候補の名前、inode、サイズ、権限、更新時刻、SHA-256 を保持した |
| 既存候補でバイト上限に到達、または次の暗号化候補が残り容量を超過 | 公開を止め、作業中の空ジョブを残さなかった。試験で上限を引き上げると、既存候補を保持したまま再試行できた |
| 中断候補、空のジョブ、想定外のファイル、ハードリンク | 中断候補と空のジョブを上限に計上した。想定外のファイルとハードリンクは保存を止め、保管場所の内容を保持した |

## 強制終了や同期エラーで残った空ジョブの整理

空ジョブだけで保管件数の上限に達した場合も、DB をロックせずに整理して再保存できるか、作業用コピーで検証した。復旧用ディレクトリの固定ロックを排他で取得し、`job-<32 桁の小文字 16 進数>` に該当するディレクトリを名前順に調べる。シンボリックリンクをたどらず、実効 UID が所有する権限 `0700` のディレクトリで、隠しファイルを含めて中身が空のものを 1 件だけ確認画面に示す。既定の応答はキャンセルにした。

確認後は排他ロックを取り直し、名前、デバイス番号、inode、変更時刻と空であることを再確認する。削除には `unlinkat(..., AT_REMOVEDIR)` を使い、最終的な空判定はカーネルに委ねる。削除後に保管ディレクトリを同期し、同期に失敗した場合は画面で区別する。根拠は作業用の `prototype/CoreSession.cpp:343` の空ジョブの識別、同ファイルの `:450` の検索、`:470` の削除、`prototype/gtk_probe.cpp:815` と `:852` の確認画面と検索操作。

### 確認済み

| 条件 | 結果 |

## 試験用 deb の実行時依存と開発環境からの分離

前節の KeePassXC 2.8.0 版では、本体の ELF に開発用 sysroot の絶対パスが `RUNPATH` として残っていた。今回は作業用コピーのリンクコマンドからその指定を外した。2.8.0 と `develop` の両方で作り直し、各アーカイブから展開した本体とファイル選択ヘルパーに `RPATH` と `RUNPATH` がないことを `readelf -d` で確認した。アーカイブの内容は前節と同じ 3 ファイル。根拠は作業用の `build.py:27`、`package.sh:19` と `:25`、`audit-runtime.sh:18`。

### 確認済み

| --- | --- | --- |

### 文字倍率が届かない原因

1024×600 で文字倍率を 125%、150%、200% に変えても、試作の復旧確認ダイアログの同じ見出しは撮影画像上で 232×18 ピクセルのままだった。同じセッションで通常の GTK / libadwaita の比較用画面には文字倍率が反映された。診断を加えた試験用 deb `0.0.3~upstream` では、試作本体の `gtk-xft-dpi` は既定値 `-1`、同じ文字列の描画幅は文字倍率 100% と 200% でともに 174 ピクセルだった。通常の設定ディレクトリと隔離した設定ディレクトリで同じ結果だった。根拠は作業用の `scaling-in-app-metrics.log` と診断用 `prototype/gtk_probe.cpp:374`。

KeePassXC 由来の `Bootstrap::disableCoreDumps()` は Linux で `PR_SET_DUMPABLE=0` を設定する。VM では、この設定を GTK 初期化前に有効にした最小の比較用プログラムでも、ポータルの `Settings.ReadAll` が `AccessDenied` になり、`/proc/<pid>/root` を開けないというエラーが出た。保護を設定しない比較では同じ呼び出しが成功し、文字倍率 200% で 192 DPI が届いた。この失敗は保護された本体で発生した。ファイル選択は別プロセスの既存ヘルパーを通り、試験を完了できた。根拠は上流の `src/core/Bootstrap.cpp:94`、作業用の `prototype/CoreSession.cpp:450`、`prototype/file_picker.cpp:126`、`scaling/font-metrics.py:4` と `:14`。 [XDG Desktop Portal の関連報告](https://github.com/flatpak/xdg-desktop-portal/issues/1490)

### 実際に文字を拡大した追加試験

保護を有効にしたまま、VM の試験専用 GTK プロファイルに 192 DPI を設定した。本体と復旧確認ダイアログに 192 DPI が反映され、同じ文字列の描画幅は 347 ピクセルになった。1024×600 で別名復旧と再ロックを完了できた。一方、確認画面を開いた時点で本文が縦にスクロールした状態になり、見出しの一部が上端で切れていた。下部のキャンセルと復旧ボタンには到達できた。GNOME の設定を保護された本体に反映する経路と、大きい文字での確認画面の初期表示は未解決。根拠は作業用の `scaling/run-ui.sh:55`、`scaling-forced-in-app.log` と `forced-text-opening.png`。

## 別名復旧の書き込み処理中にサスペンドを要求

Ubuntu 26.04.1 VM の GNOME Shell 50.1 / Wayland に前節の deb `0.0.4~upstream` を導入した。ext4 上の、キーファイル単独で保護した合成 KDBX 4.0 の中断候補を使った。既存の試験用フックを試作プロセスに読み込ませ、無名の出力ファイルを同期する直前と、公開開始を確定してから最終名を付ける直前の二箇所で処理を一時停止した。各ケースは別の VM 起動で行った。根拠は作業用の `restore-desktop-lock/lock-gate.cpp:75` と `:84`、試作の `prototype/CoreSession.cpp:141` と `:639`。

処理の一時停止を解除すると、QMP で両ケースとも要求から約 1.7 秒で停止状態 `suspended` に入った。QMP で復帰させ、ゲストのカーネルログで ACPI S3 の進入・復帰を照合した。復帰時に `PrepareForSleep(false)` が届き、試作は新しい遅延用ファイルディスクリプターを取得した。根拠は作業用の `suspend-write/ui-test.py:340` と `:349`、`drive-suspend-write.py:59`、各ケースの `*-final.log` と `*-kernel.log`。

| サスペンド要求時に止めた位置 | 復帰後の結果 |
| --- | --- |
| 暗号化バイト列を書いた無名ファイルの同期直前 | 別名復旧を取り消し、保存先は空のままだった。元 DB と候補を保持し、復帰後に候補を選び直すと別名復旧できた |
| 公開開始を確定し、`linkat` で最終名を付ける直前 | 処理を再開すると公開と同期を完了した。復帰後に最終名のファイルが 1 個あり、候補とバイト単位で一致し、パーミッションは `0600` だった |

## 暗号化スナップショットの作成中にサスペンド上限へ達する場合

### ソースで確認したこと

### 出力の拒否と再試行

### VM での確認

### 設計上の判断

出力デバイスでの中断は、ファイル公開前の保護や再試行には使える。鍵導出中や書き込み呼び出し自体が停止している間は中断を届けられず、未保存の編集を持つセッションにそのまま適用してロックすると、編集が失われる。通常のサスペンドでは、まず表示と入力を閉じ、暗号化済みの復旧候補を確定させる経路を維持する。サスペンド前に DB の解放を保証するというリリース上の主張は保留する。

さらに厳格な動作を検証する場合は、編集の世代を識別できる同期済み KDBX 復旧点を通知前から持てるかを先に試す。上流ライターによる復旧点が確認できれば、DB を別プロセスに隔離する案を検証できる。未反映の編集があるときの挙動と、コアの終了を確認できない場合の扱いは設計課題。期限前のプロセス終了やメモリの消去は今回評価していない。システム全体のサスペンドを無期限に抑止する方式は、OS の権限や電源操作に依存するため採用しない。 [Ubuntu のサスペンド抑止の仕様](https://manpages.ubuntu.com/manpages/resolute/man1/systemd-inhibit.1.html#OPTIONS)

## サスペンド通知前の暗号化済み復旧点

編集済みの世代と、ストレージへの同期を確認した世代を分ける小規模なコア試験を作業用ディレクトリに作成した。既存の `CoreSession::saveCopy()` を再利用し、編集ごとに専用ディレクトリに新しい世代番号の KDBX を作る。ライターは上流 KeePassXC のまま。作業用のディレクトリは先に作成して同期し、KDBX は `0600` の無名ファイルへ書いてファイルを同期してから、既存ファイルを置き換えずに公開する。ファイルとディレクトリの同期がどちらも成功した時点でのみ、呼び出し側の確定済み世代を進める。根拠は作業用の `pre-suspend-checkpoint/prototype/fault_probe.cpp:19`、`:28` と `prototype/CoreSession.cpp:87`、`:141`、`:729`。 [ext4 のジャーナルと書き込みの順序](https://docs.kernel.org/filesystems/ext4/journal.html)

Ubuntu 26.04 のカーネルを使う QEMU 検証 VM の ext4 で、2 回の編集と復旧点の確定を終えてから、3 回目の編集の保存中に VM 全体を強制停止した。前回の GUI 試験の S3 サスペンドとは別に、今回はディスクに残る世代を再起動後に確認した。上流 2.8.0 と比較用 `develop`、raw ディスクと未同期の書き込みを破棄する NBD モデルを組み合わせ、合成 KDBX 4.0 だけを使用した。

### 確認済み

6 通りの停止点を 2 ビルド、2 ディスクモデルで試した。24 ケースすべてで、再起動後に第 1・第 2 世代の SHA-256 が停止前と一致し、上流 CLI でそれぞれの編集を確認できた。元 DB の SHA-256 も全ケースで一致した。

| 第 3 世代の停止点 | 停止前に通知された確定世代 | 再起動後に開けた世代 |
| --- | --- | --- |
| Argon2 の入口、無名ファイルの同期直前 | 2 | 1、2 |
| 名前を付けた直後、ディレクトリ同期の前 | 2 | 1、2 |
| ディレクトリ同期が `EIO` を返した後 | 2 | 1、2 |
| ディレクトリ同期の成功直後、呼び出し元への通知前 | 2 | 1、2、3 |
| 呼び出し元が同期成功を確認した後 | 3 | 1、2、3 |

ディレクトリ同期が失敗したケースでは、同じ名前への再試行も既存のファイルを上書きせず、確定済み世代を進めなかった。同期完了から通知までの間に停止したケースでは、通知されていない第 3 世代も再起動後に検証できた。NBD モデルでは今回の停止時点に未フラッシュのセクターはなかった。物理ストレージの電源断や部分書き込みは、この結果から判断できない。

停止点は作業用の `pre-suspend-checkpoint/checkpoint-gate.cpp:69`、`:77`、`:80`、`:85`、`:94`、照合は `run.py:75`、`:95`、`:106` と `init:36`、`:56`。試験コードとログは `/tmp/keepassxc-phase2.YxadbPNq/pre-suspend-checkpoint` に置いた。通常環境へのパッケージ追加は不要だった。

### 設計上の判断と残る条件

復旧点が確定済みかどうかは、ファイル名が見えることと分けて管理する。次の試作で別プロセスのコアを扱う場合は、コアの停止を判断する側へ、同期が済んだ世代を明示的に通知する。最新の編集世代と一致している場合に限り、その編集を復旧点から取り戻せると判断する。差がある場合は保存待ちを表示し、保存できたと扱わない。再起動後の候補は上流ライターと互換の読取処理で認証・検証してから扱う。ファイル名の世代番号は今回の専用試験ディレクトリ内での識別用であり、DB の由来や世代番号自体を認証する仕組みは未設計。

今回の試作は復旧点の作成と復元可能性に限る。実際の UI で編集のたびに全体を暗号化する場合の待ち時間、保存先の容量制限と世代の整理、元 DB の変更や鍵変更後の復旧点の扱い、サスペンド時のコア停止は別の検証項目。復旧点には編集時点の秘密情報が含まれるので、保持・削除の方針も決める必要がある。

## サスペンド前のコアプロセス終了

作業用試作で、KeePassXC 2.8.0（`1c2f23ef5914c0f442a00533def1689857afb5a7`）の DB オブジェクトを子プロセスに置き、監督プロセスが logind の遅延用 FD を所有する構成を試した。子は上流ライターで暗号化し、ファイルとディレクトリを同期した後にのみ世代番号を通知する。監督側は発行済みの最新編集の世代が通知済みの世代と一致し、専用ディレクトリ内の復旧点が通知時のファイルと一致する場合に限り、`pidfd_send_signal()` で子に `SIGKILL` を送る。シグナル送信の成功と終了確認を分け、`pidfd` が終了を示し、`wait()` で子を回収した後に遅延用 FD を閉じる。根拠は作業用の `suspend-core-process/prototype/fault_probe.cpp:11`、`:46` と `supervisor.py:64`、`:78`、`:85`、`:108`。 [Linux の pidfd と終了確認](https://man7.org/linux/man-pages/man2/pidfd_open.2.html#NOTES)

## GTK アプリ再起動後の復旧点の検出

独立した作業用試作で、GTK プロセスが終了しても合成 DB の復旧点を選べるようにした。専用ディレクトリのファイル名から最大の世代番号を探し、前回確認済みの世代番号を記録した `.head` に該当するファイルが存在することを確認する。復旧点が見つかってもロック画面を維持する。復旧候補はファイル記述子で子プロセスに渡し、上流 KeePassXC 2.8.0 のコアで解除する。解除後は KDBX 内の暗号化されたメタデータから、元 DB の暗号化ファイルの SHA-256 と世代番号を照合する。両方が一致して初めて、必要なら `.head` を同期して編集画面に進む。根拠は作業用の `gtk-recovery-restart/recovery_catalog.py:74`、`:86`、`:99`、`:117`、`resume_ui.py:176`、`:349`、`prototype/fault_probe.cpp:51`、`prototype/CoreSession.cpp:742`、`:757`。上流のメタデータの読み書きは `src/format/KdbxXmlReader.cpp:309`、`src/format/KdbxXmlWriter.cpp:169`、KDBX4 の HMAC 検証は `src/format/Kdbx4Reader.cpp:77`、`:82`。 [KeePass の KDBX 仕様](https://keepass.info/help/kb/kdbx.html)

`.head` はファイルを同期してからアトミックに置き換え、ディレクトリも同期する。上流ライターが KDBX を同期した後、`.head` を更新する前にアプリが終了しても、次回起動時に新しい候補が残っていれば、認証と照合後に確認済み世代を進められる。記録が指すファイルの欠落や、最大世代の認証・照合の失敗時は、自動で元 DB や古い復旧点を開かない。 [ファイルとディレクトリの同期](https://man7.org/linux/man-pages/man2/fsync.2.html)

## 復旧点の保持上限と安全な整理

単一の合成 DB を扱う作業用試作で、通常は最新と直前の 2 世代を保持し、次の保存を確定する間だけ 3 件目を許す。すでに 3 件ある場合や、以前の整理が同期まで完了したことを確認できない場合は、GTK が編集命令をコアへ送る前に停止する。既存の件数が上限を超えていても、確認できないファイルを削除して枠を空ける処理は行わない。根拠は作業用の `gtk-recovery-retention/recovery_catalog.py:12`、`:168` と `resume_ui.py:464`。

コアは前回と同じ上流 KeePassXC 2.8.0 の試験バイナリを使う。上流コアから新しい KDBX の同期完了を受け取った後、または再起動後に候補を認証して開いた後に、暗号化ファイルの SHA-256 と世代番号を記録する。ファイルを同期してから記録 `.head` をアトミックに置き換え、保存先のディレクトリを同期する。その後に、保持する最新と直前のファイルを記録と照合する。削除対象も記録と一致する場合に限り名前を削除し、ディレクトリを再度同期する。旧形式の世代番号だけの記録は読めるが、照合履歴のない旧世代は削除対象にしない。根拠は `recovery_catalog.py:94`、`:171`、`:180`、`:198`、`:220`、`:250`、`resume_ui.py:608`。 [ファイルとディレクトリの同期](https://man7.org/linux/man-pages/man2/fsync.2.html)、[Linux の unlinkat](https://man7.org/linux/man-pages/man2/unlink.2.html)

試作同士の書き込みは専用ディレクトリの `.lock` を `flock()` で保持して直列化し、子にも同じファイル記述子を渡す。監督側のプロセスが終了しても、子のファイル記述子が閉じるまで同じロックが残る。根拠は `recovery_catalog.py:50` と `resume_ui.py:447`。 [Linux の flock の寿命](https://man7.org/linux/man-pages/man2/flock.2.html)

### 確認済み

| 条件 | 結果 |
| --- | --- |
| GTK から 5 回保存し、アプリを再起動 | 第 2 世代以降の各保存後に最新と直前だけが残った。再起動後に第 5 世代を解除でき、以前の復旧点の画面には第 4 世代だけが表示された |
| 新しい復旧点のファイル同期、または記録置換後のディレクトリ同期が失敗 | その場で既存の候補を削除せず、3 件すべての SHA-256 が一致した。再起動後に第 3 世代を認証して同期し直すと整理できた |
| 確認済み世代の記録を同期した直後、整理前にプロセスが終了 | 3 件と第 3 世代の記録が残った。再起動後に候補を認証して第 2・第 3 世代に整理できた |
| 古いファイルの削除、または削除後のディレクトリ同期が失敗 | 削除失敗では 3 件すべてを維持した。削除後の同期失敗でも保持対象の 2 件を維持し、次の作成を止めた。再起動後に同期を確認すると作成枠が戻った |

## 復旧点の容量上限

## 旧形式の復旧点を保管して保存枠を空ける

独立した作業用試作で、照合履歴のない旧形式の記録で保存枠が埋まった場合に、利用者が復旧点を保管してから整理できるようにした。最新の記録とファイル一覧が一致するときに、最新 2 世代より古い復旧点だけを対象にする。子プロセスは選択した候補と保持する 2 世代を上流 KeePassXC 2.8.0 のコアで解除し、暗号化された元 DB の識別情報と世代番号を各ファイルで照合する。根拠は作業用の `gtk-legacy-recovery-cleanup/recovery_catalog.py:170`、`resume_ui.py:307`、`:429` と `prototype/CoreSession.cpp:825`。

## 別のファイルシステムへの復旧点の保管

作業用試作で、旧形式の復旧点を別のローカルファイルシステムへ保管してから整理できるようにした。別デバイスを許可する条件は `fstatfs()` が ext 系のファイルシステム種別を返す場合に限った。Linux の種別値は ext2、ext3、ext4 で共通であり、今回は ext4 で検証した。保管ファイルが選んだ保管先デバイス上にあり、元候補と同じデバイス・inode の組み合わせではないことを確認する。根拠は作業用の `gtk-legacy-cross-filesystem/prototype/CoreSession.cpp:854`、`:921`、`prototype/fault_probe.cpp:70`。 [Linux の fstatfs とファイルシステム種別](https://man7.org/linux/man-pages/man2/statfs.2.html)

## 復旧点の整理中のサスペンド

作業用 GTK 試作で、復旧用の子プロセスが動作している間は、サスペンドから復帰してロック画面を表示していても解除操作を受け付けないようにした。ボタンとパスワード欄に加え、解除処理自体も同じ条件で保護する。確認待ちでサスペンド通知を受けた場合は、確認画面を閉じて子にキャンセルを送る。削除を確定した後は処理の終了を待ち、子の終了を確認してから logind の遅延用 FD を閉じる。logind が先に遅延上限に達した場合は、復帰後も処理が終わるまで待機を表示する。根拠は作業用の `gtk-legacy-cleanup-suspend/resume_ui.py:480`、`:500`、`:544`、`:648`、`:659` と、前回と同じコアの `gtk-legacy-cross-filesystem/prototype/CoreSession.cpp:933`、`:943`。 [Ubuntu の logind の遅延上限](https://manpages.ubuntu.com/manpages/resolute/man5/logind.conf.5.html)

Ubuntu 26.04.1 検証 VM の GNOME / Wayland 上で、復旧用ストレージと保管先を別々の ext4 仮想ディスクに置き、合成 KDBX 4.0 を使った。二つの条件を別々の VM 起動で試し、実際の `PrepareForSleep(true/false)`、QMP の `SUSPEND/WAKEUP` とカーネルの S3 記録を照合した。

### 確認済み

| 条件 | サスペンドと復帰の結果 |
| --- | --- |
| 保管コピーを同期し、削除確認を表示している間にサスペンド | 確認画面を閉じてキャンセルを送った。子の終了を確認して遅延用 FD を閉じ、要求から 0.45 秒で S3 に入った。復帰後はロック画面を維持し、元の候補と保管コピーの SHA-256 が一致した |

両ケースで保管コピー、保持対象の第 2・第 3 世代、元 DB の SHA-256 は一致した。復帰後、処理が終了してからパスワードを入力し、第 3 世代を開けた。保管ディスクを読み取り専用で再マウントして回収し、上流 CLI で保管コピーと残った各世代を照合した。根拠は作業用の `kdf-gate.cpp:137`、`ui_test.py:274`、`:288`、`:297`、`:304` と `gtk-legacy-cleanup-suspend-*-final.log`、`*-kernel.log`、`gtk-legacy-cleanup-suspend-verify-cli.log`。試験資材は `/tmp/keepassxc-phase2.YxadbPNq/gtk-legacy-cleanup-suspend` と `/tmp/keepassxc-gnome-vm.RfOXVVT9` に置いた。パッケージの追加は不要だった。

### 残る条件

削除確定後から削除を呼び出すまでの各停止点、保管コピーの作成途中でのサスペンド、同期エラーとサスペンドが同時に起きる場合は、今回の二条件とは別。物理機、電源断、メモリの消去は未検証。

## 復旧点の保管コピー作成中のサスペンド

前節の GTK 試作とコアの実行ファイルをそのまま使い、Ubuntu 26.04.1 の GNOME / Wayland 検証 VM で、別々の ext4 ディスク間に合成 KDBX 4.0 を保管した。今回は試験用フックで `O_TMPFILE` への書き込み途中、または保管コピーを名前で公開してから保管先ディレクトリを `fsync` する直前に子を止めた。`O_TMPFILE` は名前が公開されるまでディレクトリ一覧に現れず、ファイル自体の同期とディレクトリの同期は別の操作になる。根拠は `gtk-legacy-cross-filesystem/prototype/CoreSession.cpp:129`、`:144`、`:904`、`:926`、`prototype/fault_probe.cpp:60` と `gtk-legacy-archive-suspend/kdf-gate.cpp:174`、`:192`。 [Linux の O_TMPFILE](https://man7.org/linux/man-pages/man2/open.2.html) [Linux の fsync](https://man7.org/linux/man-pages/man2/fsync.2.html)

GTK 側はサスペンド通知で削除の同意をキャンセルする。子が保管中なら処理は続けられるが、後で `ARCHIVE_READY` が届いても、その操作について削除確認は表示しない。子が終了するまでは復帰後もロック解除と他の復旧操作を無効にする。根拠は `gtk-legacy-archive-suspend/resume_ui.py:462`、`:544`、`:648`、`:708`。

### 確認済み

| 停止点 | S3 と復帰後の結果 |
| --- | --- |

利用者が GNOME のシステムメニューからスリープに入り、実機を復帰させた。`/sys/power/suspend_stats/success` は 6 から 7 になり、`CLOCK_BOOTTIME` と `CLOCK_MONOTONIC` の差は約 2.0 秒増えた。試作で logind の `PrepareForSleep(true/false)` と子の終了を確認し、復帰時はロック画面を維持した。合成パスワードで再認証してから内容を開け、元 DB のハッシュは一致した。根拠は `sleep-baseline.log`、`sleep-after.log`、`lock-sleep.log` と `lock-sleep-manual-app.log`。

利用者が試作用フォルダーをファイル選択画面で確定し、第 1 世代の復旧コピーを保存した。元 DB と既存の 2 世代はハッシュを維持した。上流 CLI で復旧コピーを開き、KDBX 4.0 のヘッダーと対象エントリーを確認した。最初の自動操作では試作のフォルダー選択ボタンを AT-SPI で検出できず、この操作は利用者が行った。根拠は `file-picker.py`、`file-picker-manual.log` と `file-picker-verify-cli.log`。

最初の実機試験は、GNOME Shell とポータルの `LANG=ja_JP.UTF-8` に対し、Codex から起動した試作が `LC_ALL=C.UTF-8` を継承していたため、試作側の文言が英語になった。日本語の GTK・GNOME カタログは実機に存在した。試作は GLib のメッセージ用言語から表示を選ぶ。根拠は展開済み `resume_ui.py:122`、`:125` と実機のセッション環境。

試作の起動環境だけで `LC_ALL`、`LC_MESSAGES`、`LANGUAGE` の上書きを外し、GNOME と同じ `LANG=ja_JP.UTF-8` で再試験した。ウィンドウのタイトル、「ロック解除」、「別名コピーを保存」の日本語表示を AT-SPI で確認した。根拠は `japanese-check.py` と `japanese-check.log`。

実機での確認範囲は、展開した同一 deb による合成データの操作、GNOME 画面ロック、`s2idle`、ファイル選択と日本語表示。実機での APT インストール・削除と、配色や表示倍率を変更した回帰試験は VM の検証記録と区別する。
