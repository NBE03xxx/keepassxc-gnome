## 実機で見つかった修正

### GNOME 50 の idle-inhibit proxy

`org.gnome.ScreenSaver.GetActive` は正常だが、`org.freedesktop.ScreenSaver.GetActive` は `org.freedesktop.DBus.Error.NotSupported` を返す。後者の標準 API は idle の抑止であり、GetActive を必須にしてはいけない（[公式仕様](https://specifications.freedesktop.org/idle-inhibit/latest/)）。従来は補助 API の失敗もロック中と判断し、GNOME の正常なロック状態と logind の猶予 FD が確認できても操作を禁止していた。

FDO の未対応（NotSupported / UnknownMethod / UnknownInterface）を区別し、GNOME 側が所有者・現在状態を確認できているときだけ、未対応の補助問い合わせを必須条件から外す。実ロック・サービス消失・AccessDenied 等は従来どおり停止する。logind と猶予 FD は必須のまま。固定的な未対応の問い合わせを毎秒再試行しない。サービス所有者が変われば能力を再評価する（`src/gnome/SessionGuard.cpp`）。私有バスに GNOME 50 の応答を追加して回帰試験した（`tests/lifetime_tests.cpp`）。

### ダイアログ監視モデルの参照

GUI の LSan 報告から、`adw_application_window_get_dialogs()` の戻り値を解放していなかった利用側の32バイト1件を特定した。API の所有権は full であり、ダイアログの参照を確保した後で model の参照を返すよう修正した（`src/main.cpp`）。ロック前後の model 参照数の回帰確認と ASan アクセス検査が成功した。修正前後の LSan は 2,604,567 / 66,317 → 2,604,535 bytes / 66,316 allocations で、該当の GLib / Adwaita / conceal 起点の直接リークが消えた。

残る報告を単にアプリの問題ではないと扱わない。今回の GUI workload の割り当て起点は Fontconfig で、アプリを含まない GTK 単独の対照でも再現する。対照で GDK display を閉じて main context を処理しても終了時報告が残った。全体の LSan ゼロを達成したとは報告しない。抑制設定やメモリ検査の無効化で合格にはしない。

## 支援技術の操作と試験ドライバー

実機試験では AT-SPI 経由の操作で GDK の key / pointer イベントが発生しない場合があり、操作していても以前の無操作時刻のままになっていた。共通ボタンの操作で期限を検査し、既に期限切れならロックして古い操作を捨て、期限内なら操作時刻を更新する。5分の期限を延ばしたり、ロックを回避する処理は加えない。GUI の寿命試験へ回帰確認を追加した（`src/main.cpp`、`tests/lifetime_ui_probe.cpp`）。

AT-SPI のクライアントはイベント処理と cache 更新が必要だった。試験ドライバーで古い閉じた dialog を現行の画面と混同しないよう修正した。また利用者が保存した後に自動試験が別の合成 DB を作り直してしまったため、保存済み fixture があれば新規作成を拒否するガードを追加した。既存の `host-native.kdbx` の内容・ハッシュは維持しており、未保存表示は後から作った別の合成モデルだった。

利用者が Native FileChooser で fixtures/host-native.kdbx を保存した。本家の無変更 CLI で再解除し、AES-256 / Argon2id、2グループ・1エントリーの合成データを確認した。以後はこの保存済みファイルを再利用し、別の未保存 DB を自動で新規作成しない。

## 実スリープと復帰

再び保存済み DB を解除し、エントリー編集を表示した。今回は AT-SPI の編集フォーム配下の取得がタイムアウトしたため自動入力を中止し、利用者が入力欄の表示を確認した。スリープ試験では未確定の新規入力を追加したとは扱わず、既存の合成項目が入った編集画面の消去を確認した。

利用者が GNOME のメニューでサスペンドし、復帰・OS のロック解除を行った。16:37:59.962 に PrepareForSleep(true)、16:38:00.117 に子プロセスなし、同 .118 に delay inhibitor なしを観測した。16:38:19.635 の PrepareForSleep(false) 後に inhibitor が再取得され、16:38:25.493 に GNOME のロック解除通知を受けた。boottime と monotonic の差も停止期間中に増加した。復帰後の `verify-lock` は成功し、保存済み DB の hash は不変だった。実機観測だけで猶予時間内の厳密な全順序を証明せず、FD 解放と停止の契約は既存の私有バス回帰試験と合わせて評価する。
