## 判定

**コア再利用、既知データの保持、保存・復旧、自動ロックの実装と既存検証を確認し、初回D-Bus接続失敗の受付を1件修正した。[修正版dev5の作成・VM検証](session-guard-candidate-validation.md)と、[同じ候補の実機更新・今回のOrca確認](dev5-physical-orca.md)を完了した。** 実機の導入版は `0.1.0~dev5-1`。明示した伏せ字での文字非読み上げは確認したが、初回のqzv読み上げ報告は入力条件不明・原因未特定の観測として残す。実データ利用の合格判定、公開用バイナリの固定、GitHubへの公開は行っていない。

今回の確認は下表の経路と回帰試験を対象とする。全ソース・全依存・全脆弱性の外部監査や、物理的な電源断試験を実施したという意味ではない。

## 修正した初回D-Bus接続失敗

**再現確認。** `g_dbus_proxy_new_for_bus_finish()` が失敗した場合、旧処理はendpointを初期化済みにするだけだった。所有者もactive状態も無いため、初期化完了後に `blocked()` がfalseになり得た。警告表示はあるが、監視できない状態でDB作成・解除の受付が可能だった（修正前 `src/gnome/SessionGuard.cpp:121`、`src/main.cpp:406`、`:572`）。

**修正済み・自動検証済み。** proxy作成失敗ではendpointをactive / failedにし、ロック通知と利用不可の通知を出す。`blocked()`を維持して作成・解除を禁止する。セッションバス・システムバス・両方が接続不能の3通りを、それぞれ新しい実行プロセスと、試験専用の存在しないsocketで再現する。通常の実機バス・ロック・スリープは操作しない（`src/gnome/SessionGuard.cpp:121`、`tests/lifetime_tests.cpp:49`、`:59`）。

修正前に追加試験が `bus connection failure cannot certify an unlocked desktop` で失敗し、修正後は3通りとも成功した。GLibが保持する接続の再利用で失敗を隠さないよう、子プロセスはexecし直している。製品に試験用の認証回避や環境変数分岐は追加していない。

この初期接続失敗の後にproxyを作り直す機能はまだない。バスを復旧した後、アプリを起動し直して監視の開始を確認する。既に確立したproxyについて、サービス所有者の再出現・状態取得・sleep猶予の再取得は既存の処理を使う。

**保持した設計上の境界。** バスに正常接続できても、起動時から監視サービスの所有者が存在しない分離環境等では、従来どおり警告を表示して操作を許可する。無操作・復帰時計のロックは有効だが、画面ロック・サスペンド前の保護を保証する環境ではない。所有者消失や問い合わせ拒否・失敗によるロックとは区別する。これは対象GNOME環境の正常な監視を確認した結果に読み替えず、警告が残る通常環境での実データ利用を合格とは扱わない（`src/gnome/SessionGuard.cpp:53`、`:160`、`:164`、`src/main.cpp:188`）。
