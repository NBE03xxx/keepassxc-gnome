# 読み込み処理の資源制限と中断

更新日：2026-11-13。対象：Phase 3 の実施手順2。上流基準：KeePassXC 2.8.0、`1c2f23ef5914c0f442a00533def1689857afb5a7`。

## 実装した範囲

**実装・確認済み。** 製品の GTK 経路では、KDBX の読み込み・鍵導出と解除後のモデルを専用の `keepassxc-gnome-worker` 子プロセスに移した。GTK 側の Qt スレッドは子プロセスとの通信を制御し、一覧や個別操作に必要な値だけを受け取る。親プロセスでファイルを再解析する経路は追加していない。暗号処理・形式処理には引き続き既存の `CoreSession` と KeePassXC を使い、上流の参照チェックアウトと既存パッチは変更していない（`src/gnome/session_worker.cpp:44`、`src/gnome/RemoteSession.cpp:170`、`src/main.cpp:39`）。

読み込み後も子プロセスを使うため、グループ・エントリー操作、検索、コピー、別名保存は同じモデルに対する要求として送る。親の静的なパスワード生成処理等まで Qt / KeePassXC 依存を排除する変更ではない。

## 既定の上限

| 対象 | 制限 | 検査する場所 |
| --- | --- | --- |
| 子プロセスの仮想アドレス空間 | 1 GiB、soft / hard とも固定 | `src/gnome/ProcessPolicy.h:12`、`:41` |
| CPU 時間 | 読込・通常操作は1要求につき15秒、手順3追加の保存要求は45秒の追加予算。累積使用量の秒単位への切上げにより最大約1秒の余裕が付く | 同ファイル `:28` |
| 経過時間 | 起動・要求の送受信・応答待ちを含め、読込・通常操作は1要求につき30秒、保存要求は90秒 | `src/gnome/RemoteSession.cpp:79`、`:170` |
| 通信の1フレーム | UTF-8 JSON 本文16 MiB。長さ宣言を検査してから受信バッファを確保 | `src/gnome/SessionProtocol.h:16`、`:83` |
| 同時に保持する子プロセス | モデル用1つ。手順3で復旧用の補助を最大1つ追加。各ワーカーは旧プロセスの回収待ち中に新規起動しない | `src/gnome/RemoteSession.cpp:31`、`:125` |
| 書込ファイルの長さ | 手順3で `RLIMIT_FSIZE` の soft/hard 128 MiB を追加 | `src/gnome/ProcessPolicy.h:62` |
| 実行用スレッドプール | 子プロセス内の Qt プール2、Botan プール2 | `src/gnome/session_worker.cpp:52` |

これらは既存のファイル128 MiB、展開256 MiB、XML 深さ・モデル件数、KDF の型・パラメーター上限と組み合わせて使う。試験は既定値以下に狭められるが、0や既定値を超える指定は受け入れない。GUI に上限解除は設けていない。正当な大きい DB や重い設定も拒否しうる、開発版の利用方針である。

**制限の意味。** `RLIMIT_AS` は仮想アドレス空間の上限であり、システム全体の物理 RAM やページキャッシュの上限ではない。`RLIMIT_CPU` は全スレッドを含むプロセスの CPU 使用時間に対する累積上限なので、要求ごとに使用済み時間を加えて soft limit を設定する。継承した hard limit を引き上げる処理はない。経過時間は親が単調時計で監視する。アイドル中に30秒で DB を破棄する仕組みではなく、要求が進行している間の制限である。[Linux の資源制限仕様](https://man7.org/linux/man-pages/man2/getrlimit.2.html)

Botan の既定プールは CPU 数に応じたスレッドを用意する。本環境では最初の試験で17スレッド・約1 GiBの仮想メモリ予約を観測し、1 GiB上限下で通常の保存が失敗した。子プロセスの初期化で `BOTAN_THREAD_POOL_SIZE=2` を設定し、予約量を抑えた。これは実行スレッド数の調整であり、Argon2 の保存パラメーターであるレーン数・メモリ・反復を変更しない。別ビルドの無変更コアとの4・8レーンの往復比較でも確認した。[Botan の公式な環境変数仕様](https://botan.randombit.net/handbook/api_ref/env_vars.html)

## キャンセル・ロック・終了

GTK 側はキャンセル世代を進め、その場で画面と編集フォーム・自分のクリップボードを隠す。制御スレッドは最大10 ms程度の通信待ち単位で世代と経過時間を確認し、キャンセル・時間超過では子プロセスを `SIGKILL` で終了させる。上流の KDF を実行している C++ スレッドを途中で強制終了したり、半端な候補モデルを親に渡したりしない。

キューに入ってからキャンセルされた操作は、子プロセスを起動する前にも世代を確認する。古い応答は要求 ID と画面の世代で検査し、キャンセル後の一覧・編集画面として公開しない。ウィンドウ終了時はキャンセルしてから制御スレッドを終了する。解除・作成中にはキャンセルボタンを表示し、ロック操作も利用できる（`src/main.cpp:31`、`:103`、`:286`、`:338`、`:365`）。

終了した子は通常 `waitpid` で回収する。回収待ちは制御スレッドで250 msに制限し、それでも終わらない場合は別スレッドで待つ。その間、同じコントローラーは次の子を起動しない。

**OS による限界。** カーネル内の割り込み不能な I/O 待ちやプロセス起動自体の停止は、ユーザー空間だけで即時終了を保証できない。`SIGKILL` の発行と GUI／制御スレッドが無期限に待たない設計は行ったが、このカーネル状態を実機で故障注入した試験は未実施である。通常の待機、CPU 使用中の実 KDF、異常終了については後述の試験で回収まで確認した。

## 通信とプロセスの後始末

- `posix_spawn` で既知の同梱ワーカーを起動し、専用の Unix socket pair を標準入出力に接続する。外部へのネットワーク接続や待受ポートは使わない。標準エラーは `/dev/null` に送り、上流の診断に含まれうる内容を利用者のログへ転送しない。
- パスワードはコマンドライン・環境変数・一時ファイルに載せず、専用の通信だけで渡す。親の編集フォーム・コピー結果にも平文が存在するため、全ての秘密のコピーやメモリ残留を解決したという意味ではない。
- ワーカーは入力を処理する前に上限、core dump 禁止、dumpable 無効化、親終了時の `SIGKILL` を設定する。設定直後に親 PID を再確認し、親終了との競合も扱う。親として扱われるのは作成元スレッドである。[Linux の親終了シグナル仕様](https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html)
- 継承するファイル記述子は標準入出力・標準エラーに限定し、他は exec 前に閉じる。新しい子では通信 ID を初期化する。切断、途中で終わる応答、不正 JSON、ID 不一致、長さ超過は成功として処理しない。

この分離は資源制御と中断のためのもので、子プロセス全体のファイル・ネットワーク権限を制限する完全な攻撃隔離サンドボックスではない。

## 失敗時のモデル・保存状態

解除に失敗した場合や資源超過・キャンセル時は、一覧・詳細・コピー・保存を利用できない状態に戻す。元のファイルを黙って変換する経路はない。CPU超過と、識別できたメモリ／通信量超過を資源超過、経過時間超過を時間超過、その他の異常終了をワーカー異常として扱う。下位ライブラリが失敗を一般のエラーとして返す場合まで、原因を完全に識別できるとは保証しない。

**保存要求前の編集保護は手順4に残す。** 子プロセスが異常終了すれば、その中だけにあった未保存の編集は保持できない。読み込み後の操作が中断したときは、この可能性を画面に示す。また、保存の応答を受け取る前に停止した場合、保存先にはコピーが作成済みの場合がある。保存中断後に「ファイルは変更していない」とは表示せず、保存先の確認を案内する。保存要求開始後の復旧・耐久性は、その後の [手順3の記録](safe-save-recovery.md) で実装・検証した。保存要求前の編集保護は手順4で扱う。

## 試験と結果

**確認済み。** CTest 全16項目が成功した。追加した試験は以下である。

| 試験 | 確認した動作 |
| --- | --- |
| `gnome_process_domain_tests` | 実ワーカー経由の DB 作成、編集、検索、生成、別名保存、再解除、ごみ箱、ロック。通常の初期 KDF でも動くこと |
| `gnome_process_known_data_tests` | 無変更の本家コアとの44パラメーター組合せ・88往復。既存40組合せに、プール数と異なる Argon2d / id の4・8レーンを追加。KDF 設定と導出結果の互換性を維持すること |
| `gnome_process_tests` | 経過時間、CPU、メモリ超過、異常終了、途切れた応答、不正 JSON、ID 不一致、アイドル中の切断でも制御側を SIGPIPE で終了させないこと、受信・送信のサイズ超過、停止後の再開、子の回収、親終了時の停止 |

実際の KDF を使う中断試験では、合成 KDBX 3.1 のヘッダーに許容上限内の AES-KDF 1億回を指定し、子が CPU を使用していることを確認してからキャンセルする。暗号本文と鍵が不一致の合成入力で、認証成功を試験するものではない。CPU 使用中のキャンセルから終了・回収までが1.5秒未満であること、入力バイト列が変化しないことを確認した（`tests/process_tests.cpp:54`）。

さらに、既存の読み取り方針が IPC 経路でも維持されることを、切り詰めた暗号、KDF 上限超過、保持不能 XML、書き手のいない FIFO で確認した。0・過大のプロセス上限を指定してもワーカーは起動しない。試験では `prlimit` で実際のカーネルのアドレス空間 soft/hard、CPU、core dump の上限も照合する（同ファイル `:27`、`:176`）。

小さい合成モデルによる44組合せの観測では、子の仮想メモリの高水位は381,388 KiB、常駐メモリの高水位は27,152 KiBだった。これはこの試験入力に対する測定であり、実際の大規模 DB の最大 RAM 使用量の予測ではない。値は実行環境により変動する。

**GUI 確認済み。** 独立した GNOME Wayland セッションで、通常の日本語 UI 操作に加え、キャンセル3回、異常終了後のロック、再操作、処理待機中のウィンドウ終了を確認した。異常系 GUI 試験では実際の UI をテスト用ディレクトリへコピーし、そこにだけ試験専用ワーカーを配置する。製品ワーカーを置き換える環境変数・テスト用コマンドを製品に追加していない（`tests/ui_cancel.py:1`、`tools/test-ui.sh:10`）。

AddressSanitizer / LeakSanitizer では、直接のコア経路の XML・モデル検査323ケースと88往復、制御・IPC 経路の88往復と異常系試験に指摘がなかった。ASan の巨大な仮想シャドウ領域と `RLIMIT_AS` は両立しないため、後者では制御側を sanitizer 付き、資源制限する子を通常ビルドとする。子の reader / model 自体は前者の別試験で検査している（`tools/test-reader-memory.sh:18`）。

## 手順3による更新

保存の書出しと再検証に限って CPU 45秒／経過90秒とし、その他の操作は15秒／30秒を維持した。出力長のカーネル上限と超過試験を追加した。復旧用補助ワーカーはモデルを受け取らず、同じキャンセル世代で終了できる。現在の全体試験は17項目で、通常保存の既知データ44組合せと保存・復旧の故障試験も含む。詳細と未検証条件は [安全な保存と復旧](safe-save-recovery.md) を参照する。
