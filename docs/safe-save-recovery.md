# 安全な保存と復旧

更新日：2026-11-13。Phase 3 の実施手順3。基準：KeePassXC 2.8.0、commit `1c2f23ef5914c0f442a00533def1689857afb5a7`。

**実装・自動検証した範囲で完了。** 通常保存、新しい名前への保存、コピー保存、外部更新の検出、暗号化した復旧記録、復旧コピーの解除と新しい名前への保存、確認付きの記録削除を追加した。上流の参照チェックアウトと既存のパッチには変更していない。実 DB、既存 KeePassXC、新規パッケージ、実インストール、push は扱っていない。

これは保存要求を開始した後の保護である。保存要求より前の確認済み編集の保護は、その後の [手順4](auto-lock-secrets.md) で暗号化復旧コピーを追加した。未確定フォーム入力はロック時に消去する。電源断・ストレージ故障・通常ログイン環境のネイティブファイル選択は、以下の実装確認と区別する。

## 保存操作と状態

| 操作 | 保存先 | 成功後の編集中モデル |
| --- | --- | --- |
| 保存 | 解除時または直前の成功した「新しいファイルに保存」で関連付けたファイル | 同期・検証が全て成功した場合だけ保存済み |
| 新しいファイルに保存 | 存在しない新規パス。既存ファイルや壊れたシンボリックリンクも置換しない | 新しい保存先へ関連付けて保存済み |
| コピーを保存 | 存在しない新規パス | 保存先との関連付けと未保存状態を維持 |

新規 DB、復旧コピー、上書き元として安全性を確認できなかった入力では、「保存」は新規ファイル選択へ進む。既存の任意のファイルを選んで強制上書きする機能は設けていない。復旧コピーは解除直後から UI 上で保存が必要な状態とし、閉じる・別の DB を開く際の破棄確認を行う（`prototype/CoreSession.cpp:454`、`prototype/CoreSession.cpp:466`、`src/main.cpp:106`、`src/main.cpp:449`）。

`SaveResult` は成功、既存パス、競合、安全でないパス、使用中、I/O、書き出し、再読込検証、結果未確定、保存元なし、記録上限を区別する。ファイルの公開有無と耐久処理の完了は別のフラグとし、成功は `Committed && published && durable` に限定する。IPC 応答喪失は、公開前と断定できないため `Uncertain` として保存先・復旧記録の確認を案内する（`prototype/SaveTypes.h:7`、`src/gnome/SessionProtocol.h:63`、`src/gnome/RemoteSession.cpp:211`、`src/main.cpp:536`）。

## 暗号・形式の再利用

**確認済み。** 書き出しは公開済みの上流 `KeePass2Writer::writeDatabase(QIODevice*, Database*)` を使用する。鍵・乱数・ヘッダー・KDBX・暗号ストリームを独自に実装しない。本家 `Database::saveAs` と同様の RandomSlug 更新も維持する。書き出した暗号化候補は、上流 `KeePass2Reader` と既存の終端・KDF・展開量・XML・モデル検査を使って再解除する。保持中の CompositeKey を再利用し、検証専用のマスターパスワードを別に保存しない（`prototype/CoreSession.cpp:45`、`upstream/keepassxc/src/format/KeePass2Writer.h:40`、`upstream/keepassxc/src/core/Database.cpp:320`、`upstream/keepassxc/src/format/Kdbx4Writer.cpp:51`）。

従来の一時パスへの `Database::saveAs` 呼出しを変更した理由は、最終パスの解決・ファイル監視と編集モデルを結び付けず、開いたファイル記述子に書き出し、同期・競合判定・復旧記録をアプリ側で管理するためである。上流コアの修正や、暗号／形式処理の分岐コピーは追加していない。

再読込検証は認証と既存の読込方針への適合を確認する。あらゆる属性の同一性を都度比較する処理ではない。既知データの保持は、後述する無変更コアの明示スナップショット比較でも検証する。

## ファイルを公開する手順

**確認済み。** 保存先と同じディレクトリに、次の順で処理する（`src/gnome/SafeSave.cpp:156`）。

1. 親ディレクトリを FD として開き、対象名の専用ロックファイルを `flock(LOCK_EX|LOCK_NB)` で確保する。対象を追跡しない open と、所有者・通常ファイル・リンク数の検査を行う。上書き元が読み取り専用、シンボリックリンク、ハードリンク、別所有者等なら置換しない。
2. 通常保存では解除時の基準値と現在の全暗号化ファイルを比較する。基準値は、解除に使った同じ FD の読み込み前後の stat と、読み込んだ暗号化スナップショットの SHA-256 から採る。device / inode / size / mtime / ctime / 全体ハッシュを使い、ファイルの一部の標本だけには依存しない（`prototype/CoreSession.cpp:205`、`src/gnome/SafeSave.cpp:132`）。
3. `0700` の専用トランザクションディレクトリを作り、`prepared` の journal を同期する。通常保存では元の暗号化ファイルを独立した `previous.kdbx`（`0600`）へコピー・同期し、元とコピーを再照合する。
4. `candidate.kdbx`（`0600`）へ上流 writer で書き、flush と `fsync` を行う。上流 reader で再解除・検証し、全体ハッシュを求める。
5. 公開後にも新しい版を確保できるよう、独立した `written.kdbx` をコピー・同期する。ハードリンクで代用しない。`ready` journal と両候補・旧版のディレクトリエントリーを同期する。
6. 親パスが引き続き同じディレクトリを指すことと、通常保存元が基準値と一致することを再確認する。新規保存は `RENAME_NOREPLACE`、通常保存は `RENAME_EXCHANGE` で公開する（同ファイル `:240`）。
7. 通常保存で交換した元の inode を `displaced.kdbx` として残す。交換時の inode・内容が基準値と異なる場合は競合とする。独立した `previous.kdbx` も残すため、別プロセスが旧 FD へ書き続けても、それだけに旧版の保持を依存しない。
8. 対象ファイル・両ディレクトリの同期、公開されたファイルの照合、`committed` journal の同期まで行う。成功を返す前に編集モデルの dirty 状態を解除しない。公開後の処理失敗は結果未確定とし、編集モデルは保存済みにしない。

journal は `journal.next` の書込み・同期後の rename とディレクトリ同期で更新する。暗号化候補と旧版は自動削除しない。元のデータベースを開いて直接切り詰める処理や、部分書込みを公開する処理はない（同ファイル `:64`）。

**並行更新に関する限界。** 同じアプリ同士の保存は専用ロックで直列化する。本家 KeePassXC、同期ソフト等がこのロックを共有するわけではない。Linux の rename はファイルの内容比較と一体の compare-and-swap ではなく、最終照合と交換の間に外部更新が起こりうる。その場合は成功とせず、元の独立コピー・新しい版・交換された版を保持し、利用者に新規名での保存と確認を求める。追加更新を消してしまう無条件の自動ロールバックは行わない。外部プロセスが保持する FD への継続書込みや、保存成功後の別プロセスによる置換まで阻止する保証ではない。

`renameat2` やディレクトリの `fsync` を提供しないファイルシステムでは、非原子的な上書きへ切り替えず失敗させる。本手順は Linux のローカルファイル向けであり、ネットワーク・FUSE・同期サービス全般の耐久性を実証したものではない。

## 復旧記録と利用者の手順

各保存先の隣に `.keepassxc-gnome-save-<対象名のハッシュ先頭16桁>-<UUID32桁>/` を残す。対象ごとの排他には `.keepassxc-gnome-lock-<対象名のSHA-256>` という `0600` の通常ファイルを使う。ロックファイルを毎回 unlink して inode の異なるロックを作ることはしない。

| 記録内のファイル | 用途 |
| --- | --- |
| `journal.json` | 形式版、対象のファイル名、作成日時（UTC）、進行状態、暗号化ファイルのハッシュ。パスワード・鍵・平文エントリーは書かない |
| `written.kdbx` | 再読込検証後の新しい版の独立コピー |
| `previous.kdbx` | 通常保存前の暗号化ファイルの独立コピー |
| `displaced.kdbx` | 通常保存で交換された元の inode。競合時には別プロセスの版になりうる |
| `candidate.kdbx` | 公開前の作成途中、または公開直後に中断して残ったファイル。必ずしも新しい版とは限らない |
| `journal.next` / `lock` | journal 更新用と使用中判定用。平文 DB は入らない |

1. メニューの「復旧用ファイル」を選び、元の DB があったフォルダーを選択する。元のファイル自体が削除されていてもフォルダーの検査はできる。
2. 対象名・保存時刻・進行状態を確認して行を展開する。暗号化ハッシュとの一致は、パスワードで解除して内容を確認したこととは区別する。
3. 「コピーを開く」で通常の認証・読込検査を行う。内容を確認し、新しい名前で保存する。元のファイルへの自動復元・自動マージは行わない。
4. 必要な版を確保した後に「記録を削除」を選び、確認画面で削除する。現在解除中の復旧元の記録は、新しい名前への保存が成功するまで削除させない。コピー保存だけではこの保護を解除しない。

復旧パスは canonical な親も確認して上書き元から除外し、記録内への新規保存も拒否する。削除は形式に合う専用ディレクトリ、所有者・`0700`、使用中でないロック、妥当な journal と対象名ハッシュ、既知の通常ファイルだけを検査し、親とディレクトリの同一性も照合する。未知の子・シンボリックリンク等があれば削除せず、任意のディレクトリの再帰削除は行わない（`src/gnome/SafeSave.cpp:126`、`:266`、`:314`、`src/gnome/RemoteSession.cpp:336`、`src/main.cpp:609`）。

**保持量。** 同じ対象名について64記録に達したら、古い版を勝手に消さず次の保存を拒否する。一覧は1フォルダーにつき128記録、走査100,000エントリー、journal は4 KiB、暗号化ファイルは128 MiBまで。全対象をまとめたディスク使用量の quota ではなく、複数の暗号化コピー分の空き容量が必要である。上限・読込エラー・壊れた journal 等では一覧未完了を表示する。使用中の記録は一覧と削除の対象から外す。

journal の最初の作成より前の終了、journal の破損、削除の終盤の中断では、専用ディレクトリが一覧に出ない場合がある。自動削除はしない。この場合はアプリを閉じ、ファイルマネージャー等で隠しディレクトリの内容を確認する。KDBX があれば別の通常フォルダーへコピーして通常の解除・検証を行い、必要な版を確保してから対象を手動で整理する。関係のないディレクトリまで一括削除しない。journal 初期化前にはアプリの KDBX 書込み・最終パス公開はまだ始めない。

暗号化バックアップには過去のエントリー・鍵設定も残る。記録削除は通常のファイル削除であり、SSD・スナップショット等からの安全消去を保証しない。

## 資源制限と中断

保存には上流 writer の鍵再生成と reader の再検証があるため、保存 RPC に限り CPU 45秒・経過90秒の予算を設定する。読込・その他の RPC は CPU 15秒・経過30秒のまま。試験用に基本予算を縮めれば保存もその3倍に縮まる。KDF 設定や検証を省いて時間を短縮する処理はない。1 GiB のアドレス空間上限を維持し、書込みファイル長には `RLIMIT_FSIZE` 128 MiB の soft/hard 上限を追加した。CPU 秒単位の切上げと、カーネルの割り込み不能 I/O の限界は [手順2の記録](reader-process-limits.md) と同じである（`src/gnome/ProcessPolicy.h:12`、`:62`、`src/gnome/session_worker.cpp:80`、`src/gnome/RemoteSession.cpp:175`）。

再検証は編集モデルと別の候補モデルを一時保持する。大きいモデルや重い設定は上限に達して保存できない場合がある。その場合は候補を成功扱いせず、公開前なら元ファイルを残す。

復旧一覧・削除は同じコントローラーから専用の補助ワーカーを1つ使い、編集中モデルのワーカーを置き換えない。補助側の失敗で編集中モデルを破棄しない。補助ワーカーも同じキャンセル世代・読込時間上限・プロセス上限を使い、同じ補助ワーカーの回収待ち中には次を起動しない。最大は編集中モデル用1つと復旧処理用1つである。平文モデルを補助へ送らない（`src/gnome/RemoteSession.cpp:316`）。
