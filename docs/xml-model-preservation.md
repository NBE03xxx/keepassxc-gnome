# XML・モデル件数と保持可否の判定

更新日：2026-11-13。対象：KeePassXC `1c2f23ef5914c0f442a00533def1689857afb5a7`。

## 実装した範囲

**確認済み。** 上流の XML パーサーがモデルを作る経路に、XML 階層・要素数と実際の生成・追加箇所の予算を接続した。未知の構造等を上流が捨てる経路は、解除失敗として候補モデルを破棄する。型付きの診断は `ReadFailure::UnsupportedData` とし、上限超過やパスワード等の失敗と区別して日本語・英語で表示する。

理由を報告した上で `patches/0004-xml-model-preservation.patch:1` を追加した。参照用の `upstream/keepassxc/` は変更せず、これまでと同じコミット・ハッシュ照合でビルド用コピーに適用する。

**範囲確定：未知データの再保存は検討記録のみ。** 2026-11-13 の利用者の指示により、[検討記録](compatibility-policy.md)を保存するのみとし、実装対象・完成条件から外した。任意の未知 XML やヘッダーをモデルに取り込んで書き戻す実装は追加していない。今回行うのは、保持を確認できる既存の拡張点を通し、保持できない入力を黙って変更・保存しないための暫定的な拒否である。読み取り専用でも秘密を表示しない。未知の保護要素を飛ばすと、後続の保護値の復号位置がずれる可能性があるためである。

## 予算を検査する位置

XML の構文解析には引き続き Qt を使用する。`src/gnome/XmlPolicy.h:10` の薄いラッパーで、開始・終了要素を追跡し、上流が再帰処理へ入る前に深さと開始要素数を確認する。通常のスカラーは Qt の `readElementText` を用い、未知の入れ子は受け入れない。添付の `Value Ref` の空要素も追跡し、読み飛ばす内容がないことを調べる。DTDs、処理命令、未対応の名前空間は拒否する。

モデルは `parseGroup` / `parseEntry` の一時オブジェクトだけでなく、`getGroup` / `getEntry` が参照先のために生成する仮・正規オブジェクトと、XML reader の一時親グループも数える。履歴、添付プールと参照、文字列フィールド、カスタムデータ、アイコン、削除記録、Auto-Type 関連データは、それぞれ追加前に検査する。これらの検査と集計は `src/gnome/ReadBudget.h:71` にある。

上限で参照先の生成を停止すると null が返るため、その後のコピー処理を停止し、未接続の履歴等を後始末する。履歴の解析結果が null の場合はリストに追加しない。解除は reader の成功だけでなく、診断が成功状態であることも確認してから公開する（`prototype/CoreSession.cpp:149`）。

| 対象 | 開発版の上限 |
| --- | ---: |
| XML の深さ（KeePassFile を1とする） | 128 |
| XML 開始要素 | 1,000,000 |
| モデル生成・追加の合計 | 250,000 |
| reader が生成する Group / Entry | 20,000 / 100,000 |
| 履歴項目 | 50,000 |
| 添付の実体 / 参照 | 4,096 / 100,000 |
| 文字列フィールド / カスタムデータ項目 | 100,000 / 100,000 |
| カスタムアイコン | 4,096 |
| 削除記録 / Auto-Type 関連データ | 100,000 / 100,000 |

根拠は `prototype/ReadLimits.h:27`。各上限は組み合わせて適用し、試験では小さくできる。生成・追加した累積の個数であり、現在の画面の行数、同時に生きている個数、プロセス全体の QObject 数ではない。履歴は Entry の生成にも含まれ、別に履歴の上限も適用する。モデル合計では Entry として一度数える。Entry 内部で上流が作る属性用の QObject 等は、この Group / Entry の個数とは別である。

Qt が一つのトークンや属性リストを形成する前の最大メモリまでは、このラッパーでは保証しない。既存の復号・展開量上限と組み合わせるが、プロセス全体の RAM・CPU 時間・中断の制限は依然必要。

## 保持できない入力の検出

次を現在のアプリの解除経路で拒否する。

- 未知の XML 要素・属性、未知の保護属性値、処理命令、DTD、名前空間。未知要素は内容を読み飛ばす前に止め、警告ログにその内容を載せない。
- 既知のコンテナー内の無視される通常テキスト、スカラー内の未知の子要素、重複した単一項目。文字列属性・添付名・CustomData のキーの重複も検出する。
- 未知・重複の外側ヘッダー、未知の内側ヘッダー、繰り返せない内側ヘッダーの重複、終端フィールドに付加されたデータ。
- 添付の保護フラグのうち現在の writer がそのまま保持できない `0x00` や未知ビット。現時点では writer が出力する `0x01` のみを許可する。
- 未解決のモデル参照、重複する Group / Entry / アイコンの定義、欠けた添付参照、再保存で捨てられる未使用の添付実体。
- 辞書の将来版、真偽値や UTF-8 の正規化によって元の内容を保持できない入力。前段の KDF・辞書制限も継続する。
- 現行 writer が出力しない CustomData 項目の変更日時。Group / Entry 内の日時、および KDBX 4.1 より前の Meta 項目の日時を拒否する。Meta の KDBX 4.1 の日時は許可して往復を検査した。

正当な他実装のファイルや将来版の拡張でも拒否する場合がある。たとえば添付フラグ `0x00` は、未知ビットと同一だと判断したものではなく、現行モデル・writer の組で元の保護指定を保持できないための拒否である。元ファイルは保持し、上限や機能を黙って変更して保存する経路は提供しない。

XML の字句・バイト列を完全再現する方式ではない。コメントや表示用空白等は同一性の保証対象にしない。上流が生成・更新する `_LAST_MODIFIED` や `KPXC_RANDOM_SLUG` 等の管理情報も、通常の保存で変わる。特に RandomSlug は上流の保存処理が毎回更新する（`upstream/keepassxc/src/core/Database.cpp:320`）。

## 保持を検証した既知の拡張点

任意のアプリ用キーを含む Entry のカスタム属性と保護指定、TOTP、Meta / Group / Entry の CustomData、履歴内の属性・添付・CustomData・Auto-Type 設定、カスタムアイコン、削除記録は、対応する既存モデルに読み込む。GTK が専用 UI を実装していなくても、既存モデルが表現できるデータを一括で取り除く扱いにはしない。

合成 DB に2件ずつの添付・履歴等と任意キーの保護属性を用意し、タイトルを変更して別名保存した。再読込後に、対象外の属性・保護フラグ、添付のバイト列、TOTP の認識、Auto-Type データ、ユーザー CustomData、既存の履歴と追加履歴、グループ数、アイコン、削除記録を照合した。上流の自動管理キーだけは通常の更新を許可し、それ以外のキーを無条件に除外する比較にはしていない。日時は、入力ファイルに格納され現行 writer も出力する Meta の KDBX 4.1 項目を比較した（`tests/xml_model_policy.cpp:125`）。

## 検証結果

**確認済み。** `gnome_xml_model_tests` は323ケース成功。KDBX 3.1 / 4.0 / 4.1、圧縮あり・なしを使った。独立した Qt のトークン走査と XML の要素数・最大深さを照合した。各上限ちょうどの入力は許可し、1件・1階層超過を拒否した。深いグループ構造で開発版既定の128階層にも到達させ、モデルを公開せず停止した。

一時・正規・履歴の構成を固定した対照では、Group 7個、Entry 4個、履歴2個の生成を確認した。タグだけの個数より増えることを試験で明示している。未知の保護要素を含む入力でも、一覧・パスワード取得・保存は使えず、保存先ファイルが作成されないことを確認した。全ての合成入力で元ファイルの SHA-256 が変化しないことを検査した（`tests/ReaderFixtures.h:274`）。

既存352ケースの終端検証、196ケースの資源検査、無変更の上流 CLI との互換性、選択した上流テストと言語試験も継続する。試験の共通生成器は `tests/ReaderFixtures.h` にまとめ、暗号・KDF・KDBX・圧縮には上流の実装を用いる。故障注入の生成器は製品へリンクしない。

ログは `.cache/xml-model-policy.log` と `.cache/ctest.log`。AddressSanitizer による後始末の追加検査は `tools/test-reader-memory.sh` から再実行できる。これは既存の GCC / ASan と開発用 prefix を使い、別のビルド・設定ディレクトリで実行する。

**最終確認：成功。** CTest 12項目全て成功。別ビルドの AddressSanitizer と LeakSanitizer でも323ケースが成功し、メモリアクセス・解放・リークの指摘はなかった。最初の隔離環境では LeakSanitizer 自身のスレッド検査が追跡制約で停止したため、合成データを扱う同じ試験プロセスを通常実行環境で再検証した。ASan の仮想シャドー領域と衝突するため、ASan 版だけ試験用の1 GiBアドレス空間上限を外し、CPU 上限は維持する。製品の資源上限の代わりにする変更ではない。結果は `.cache/reader-asan.log`。

同じ最終ビルドで、独立した GNOME Wayland セッションの日本語 UI 操作も通過した。DB 作成・エントリー作成と編集・検索・グループ作成・未保存の破棄・手動ロックを確認した。新しい拒否メッセージをファイル選択から確認する実環境試験は未実施である。

## 残る課題

- 本家が通常保存する既知データの互換性と拒否条件の検証を継続する。任意の未知構造の再保存は実装対象から外し、検討記録のみとする。保護ストリームに影響しうる入力を表示する方式は採用していない。
- 全ての既知フィールドの正規化・自動修復・形式変換を網羅した保持可否の判定。今回の入力群と接点だけで、あらゆる KDBX の情報保持を証明しない。
- プロセス全体のメモリ・時間制限、処理中断、ロックと復旧、保存の耐障害性、秘密の消去とクリップボード失効。
- 独立したレビュー、ファジング、他実装・多数の入力での互換性。拒否メッセージをネイティブファイル選択から確認する VM 試験。

実 DB の利用・既存 KeePassXC の変更・パッケージ追加・実インストール・push は行っていない。実データ利用や公開の合格条件は未達のままとする。
